# R12 lights: источники света, их цена и write-back

Ветка `feature/r12-lights` (worktree `E:\SecondSonPC-r10-pacing`, от базы R12 `3dd34db`). Push не выполнялся.
Сырые данные — `E:\research\r12\runs\lights\`:
- профили и перепись — `prof1`–`prof4`;
- скрининг — `screen1`;
- корректность (POISON, кадры, Validation) — `check1`, `check2`;
- серии A/B — `ab1`, `ab2`, `ab3`;
- декомпиляция — `ghidra\dec`.

Метки: **[E]** — измерено, **[A]** — анализ кода/декомпиляции, **[H]** — гипотеза.

Сокращения:
- **база** — пресет `play.cmd` R12: `SSPC_R9_PCACHE=1;SSPC_R9_HEAP_WINDOW=1;SSPC_R10_AJM=native;SSPC_R10_SYSRT=native;SSPC_R11_EARLY_SUBMIT=256`;
- **lazy** — `SSPC_FB_LAZY_WB=1` (FB-7, существующий флаг: GPU-записи больших диапазонов не пишутся обратно в память хоста, пока их кто-то не прочтёт);
- **rea_all** — lazy + `SSPC_REA_HEAP_READS=1` (REA-2, существующий флаг: чтения кучи вершин ≥ 256 МиБ не форсируют write-back);
- **keep** — `SSPC_R12_LIGHT_LIST_KEEP=1` (новый, R12): то же, что lazy, но только для списка источников по тайлам;
- сцены: **user** — сохранение владельца, маршрут `calm` (закат, город, без дождя); **fight** — город, маршрут `fight`;
  **city** — город, маршрут `traverse`; **neon** — Neon Dash; **beach** — пляж (стоя, после поворотов камеры).

## 0. Итог

- **Свет как таковой стоит мало** [E]. На GPU: tiled CS освещения 1,6–1,8 мс, атлас теней прожекторов 0,33 мс,
  occlusion queries свечений 0,015 мс. Источников 160 (user) и 207–272 (fight) на кадр из 2000 возможных. Основная
  CPU-цена фар и фонарей — подготовка ~700–1200 draw атласа на командном процессоре; её уже пробовали ускорять в
  R10, путь вышел медленнее (§2.2).
- **Самое дорогое, что связано со светом, — write-back GPU-записей в память хоста** (5,45 + 3,08 мс GPU в user).
  Это не список света: 85 % байт — пулы частиц, 12 % — список индексов по тайлам [E, §2.1].
- **Нужен ли хосту write-back списка по тайлам — нет** [E]: CPU его не читает (0 чтений). Флаг
  `SSPC_R12_LIGHT_LIST_KEEP` убирает только его write-back: картинка та же, но FPS не меняется (§5.1) — выгоды нет,
  не включать.
- **Выигрыш дают существующие флаги FB-7/REA-2** (`SSPC_FB_LAZY_WB=1`, `+SSPC_REA_HEAP_READS=1`), A/B n = 3, ab3:
  - user: 33,14 → 41,43 FPS (+25,0 %, только LAZY_WB) / 41,75 (+26,0 %, оба флага); 1 % low 27,9 → 32,6 / 33,1;
  - city: 47,83 → 48,20 / 50,13 (+4,8 %); 1 % low 20,5 → 24,1 / 24,2;
  - fight: без изменений; Neon Dash — в пределах разброса (§5.3); пляж +8,8 % (ab2, n = 2).
- **Найден и исправлен краш FB-7** (`96d916f`): гонка в `PageTracker::OnFault` убивала игру в Neon Dash в 2 из 11
  прогонов с `SSPC_FB_LAZY_WB=1` (§4.2). После исправления — 0 крашей в 14 прогонах. Сама гонка в них не
  возникла (счётчик 0), так что исправление проверено кодом, но не повтором краша.
- **Провал 1 % low в Neon Dash (ab2: 22,0 → 18,7) не подтвердился** (§5.3). Длинные кадры > 50 мс — это кадры,
  которые долго держит командный процессор; они есть и в базе (2–34 за прогон). С ожиданиями FB-7 совпадает
  около 9 % из них. Ожидание — 2–17 мс, на фоне кадров 50–200 мс.
- **Корректность:** тест отравления (хост-копии отложенных блоков залиты 0xFFFFFFFF) в user, fight, neon и city —
  картинка цела, `[Error]` 0. Validation + Sync Validation с `rea_all` в user и fight — 0 сообщений. TDR 0 за все серии.
- **Рекомендация для play.cmd:** `SSPC_FB_LAZY_WB=1;SSPC_REA_HEAP_READS=1` — кандидат при условии `96d916f`.
  Перед включением по умолчанию нужен долгий прогон (soak) в Neon Dash и в бою с этим исправлением (§7).

## 1. Как движок обрабатывает свет

### 1.1. Список источников кадра [A]

Один глобальный список `DAT_00e17f90` (eboot App 01.07):

| Поле | Что |
|---|---|
| `+0x154` | число записей в кадре |
| `+0x158` | ёмкость, 2000 |
| `+0x330` | массив записей по 0xb0 байт (параметры источника для GPU) |
| `+0x338` | массив записей по 0x50 байт (форма/отсечение) |

`0x16df30` закрывает список кадра. Оба массива видеокарта читает как `0x2edb18000+0x55f00` (2000 × 0xb0) и
`0x2edbc3e00+0x27100` (2000 × 0x50) — это входы tiled CS `0x2edafa400` [E: привязки в `RecordDispatch`].

### 1.2. Кто пишет в список [A], сколько [E]

| Адрес | Что | user, на кадр [E] | fight, на кадр [E] |
|---|---|---|---|
| `0x19a4d0` → `0x16c430` | «data light» — источник из данных уровня (фонари, лампы, окна, неон, фары машин): `0x16c430` заполняет запись, `+0x2c` — вид, `+0x4c` — слот тени | 209 проверено, 160 в списке | 232–323 проверено, 207–272 в списке |
| `0x19a960` (вызывает `0x2e9cb0`, там `expf`) | точечный свет из кода: вид `+0x2c` = 1 всегда [A]; затухающая вспышка — временный свет эффектов/способностей [H] | 0 | 0 |
| `0x16dd50` (DMA `0x3f3ed0`) | источники частиц — пачкой копируются в список (огонь, искры, эффекты способностей [H]) | 60 | 0,5–3 |
| `0x16dcc0` | flush пачки, накопленной подсистемой (`0x19a320`: `+0xa0` — пачка источников, `+0x88` — свечения → `0x198f70`) | — | — |
| `0x1ec170` → `0x1ecf70` / `0x1ed740` | отбор data light: расстояние, маски, затем `0x19a4d0` | — | — |

Вызывающие `0x19a320` (пять подсистем, сдающих пачки света): `0x3bf640`, `0x41bb50`, `0x439650`, `0x58d2c0`,
`0x597080` [A]; какая из них машины, какая уличный свет — не установлено [H].

Вид источника `+0x2c` [E по переписи, смысл — H по строкам enum `Direction / Spot / Capsule`]:

| Вид | Смысл [H] | user | fight |
|---|---|---|---|
| 1 | точечный (point) | 63 | 57–88 |
| 2 | прожектор (spot: фары, фонари с конусом, прожекторы) | 96 | 147–168 |
| 3 | капсула (линейные лампы, неон) | 2 | 1,6–17 |

Прочее [E]:
- анимированных (мигание/движение) в user 24–26, в fight 12–16;
- пик индекса в списке 169 (user) и 257–479 (fight, по прогонам) из 2000 — переполнений 0;
- поле `+0x4c` («слот тени») у всех записей 0: слот назначается позже или поле другое [H];
- источников из кода в маршрутах 0 (способности в маршрутах не применяются).

Строки движка [A]: `SHADOW_KIND` — `ShadowMap`, `VarianceShadowMap`; маска стенсила — `LightAll`,
`EnvironmentOnly`, `CharacterOnly`.

### 1.3. Где решаются освещение, тени и свечения

- **Освещение — tiled CS `0x2edafa400`** (120 × 68 групп, footer hash `0x00000000ce1675e0`) [E]. Читает оба массива
  списка и малые cb, пишет список индексов по тайлам `0x2edc12000+0x640000` (6,25 МиБ). Этот список читают
  12 PS через точный V# (`0x2d2eb0b00`, `0x2d2ed0800`, `0x2d2ed4d00`, `0x2d2eebe00`, `0x2d2ef0400`, `0x2d2ef1f00`,
  `0x2d2f07e00`, `0x2d2f08700`, `0x2d2f0a200`, `0x2d2f0cf00`, `0x2d2f0d800`, `0x2e0493c00`) [E: `SSPC_R12_READERS_OF`].
  Процессор его не читает: чтений 0 в user и fight [E: `SSPC_DIAG_READ_WATCH=2edc12000:640000`].
  Диапазон списка лежит внутри кучи вершин 2,5 ГиБ `0x271258500+0x9d3c…`, которую привязывает vertex fetch, —
  поэтому без REA-2 каждая такая привязка требует write-back и списка тоже [E: `SSPC_DIAG_LARGE_BINDS`].
- **Тени прожекторов — атлас 1024²** (`0x304610000`): depth-only draw одного pipeline (VS `0x2dfd6af00`, PS пустой) [E].
- **Свечения (glow)** — occlusion queries движка (`0x194060`, по два запроса на источник, прокси `0x1ee0c0`/`0x1ee320`,
  результат читает CS `0x195250` → `0x1ee6a0` → `0x1ed990`, GPU → GPU) [A, `docs/LIGHT_GLOW_OCCLUSION.md` в R9].
  Наше исправление `146a3bd` считает пиксели прокси на хосте (`ZpassOnTimeline`).

## 2. Цена

### 2.1. GPU [E]

Сериализованный профиль `SSPC_GPU_PROFILE=1` (`prof1\user_gpuprof`, `prof1\fight_gpuprof`, по одному прогону; при
профиле каждый батч ждёт свой конец, поэтому сумма больше реального кадра — сравнивать доли, а не складывать с FPS):

| Что | user, мс/кадр | fight, мс/кадр |
|---|---|---|
| tiled CS освещения `0x2edafa400` | 1,80 | 1,60 |
| атлас теней прожекторов 1024² (≈ 2700 draw) | 0,33 | 0,33 |
| копии счётчиков occlusion queries свечений (0–18 запросов/кадр) | 0,015 | 0,015 |
| write-back GPU-записей в память хоста: шейдер сравнения (changed words) | 5,45 | 0,59 |
| write-back: прямые копии | 3,08 | 2,34 |
| для сравнения: q1 CS частиц `0x2edaa0c00` (80 dispatch × 100 мкс) | 8,1 | 0,33 |

Освещение как таковое (tiled CS + атлас + свечения) — около 2,1 мс GPU в user и 1,9 мс в fight. В R9
(`LIGHTING_PROFILE.md`, город в дождь) tiled CS стоил 2,69 мс: там больше источников.

Самая дорогая часть, связанная со светом, — не сам свет, а **write-back GPU-записей в хост**. Разбивка
сравниваемых байт по адресам (`prof1\user_diag`, `SSPC_DIAG_LARGE_BINDS=1;SSPC_DIAG_WB_DIRTY=1`, user, 53 036 МиБ за прогон):

| Диапазон | Чей | Доля |
|---|---|---|
| `0x26d558000+0xc00000`, `0x26f358000+0xc00000` и `0x26e158100`, `0x26ff58100` (+1 МиБ) | пулы частиц кадра A/B; пишут q1 CS частиц `0x2edaa0c00`, `0x2ad5b1f00`, `0x2ad6bbb00`, `0x2e0f58400`, `0x2e10c3500`, `0x2e0fe2700`, `0x2e07a9c00`, `0x2e08c9e00` …, каждый привязывает весь пул на запись | 85 % |
| `0x2edc12000+0x640000` | список индексов по тайлам, пишет только tiled CS | 12 % |
| прочее | — | 3 % |

Это поправка к R9 `LIGHTING_PROFILE.md`, где write-back приписывался списку света на ~76 %: в user на него
приходится 12 % [E].

### 2.2. CPU [E/A]

- Отбор и подготовка списка на потоках игры. Main при GPROF=2 (user): ожидание A `cw_emitters` 14,8 мс и
  ожидание B `cw_light` 9,2 мс на кадр [E]. Это ожидания compute (частицы и освещение) на GPU, а не работа CPU
  по отбору. Сам отбор (`0x1ec170`, ~200–320 источников/кадр) в профиле Main отдельно не виден [E].
- **Атлас теней на командном процессоре** — главная CPU-цена фар и фонарей:
  - R9 (`LIGHTING_PROFILE.md`): ≈ 2,4 мс CP и ~4 FPS в городе, где кадр держал CP (проверено диагностикой, которая
    выбрасывает эти draw);
  - R10 (`docs/R10_CP.md`): подготовка draw теней на фронтенде 1,49–1,64 мс, BindStage 0,65–0,68 мс, запись
    1,49–1,55 мс, члены run 0,73–0,85 мс на кадр (на разных потоках, не складывать).
  - В R12 user упирается в GPU (CP 20,9 < GPU 24,9 мс), fight — в оба (CP 17,8, GPU 18,6) [E, ab1].
- **Write-back нужен ли хосту для списка по тайлам?** Нет [E]: процессор его не читает (0 чтений), GPU-читатели берут
  видеопамять. Write-back нужен только для корректности на случай CPU-доступа — он остаётся (fault → write-back).

### 2.3. Атлас теней и свечения по числу [E]

- Перепись (`SSPC_R12_LIGHT_CENSUS=1`): depth-only draw шириной 1024 — 840–850 (user), 1030–1180 (fight) на кадр.
  Счётчик в `DrawFiltered` недосчитывает при пакетной записи; профиль GPU даёт 2703 (user) / 2633 (fight) draw
  pipeline атласа.
- Свечения: occlusion queries 0–18 на кадр (16–18 — в первые 23–43 с маршрута user, затем 0); копии 0,015 мс.

## 3. Повторная работа

1. **Write-back каждый кадр того, что хост не читает** [E]. Пулы частиц (12 МиБ × 2 + 2 МиБ) и список по тайлам
   (6,25 МиБ) каждый кадр сравниваются шейдером со своей тенью и изменённые слова пишутся в память хоста. Процессор
   читает их редко (пулы) или никогда (список). В user на это уходит 107 ГиБ сравнений за прогон (screen1).
2. **Привязки кучи вершин 2,5 ГиБ форсируют write-back всего, что внутри её диапазона** [E] — около 2,17 млн раз за
   прогон user (счётчик keep: «heap-size host-import readings that left its blocks kept back»), хотя vertex fetch
   не читает ни список света, ни пулы.
3. **Атлас: подготовка каждого draw заново** [A, R9/R10]: мемо стадий промахивается, потому что у каждого draw свой
   указатель cb в user data. Это уже исследовано в R10 (`SSPC_R10_NATIVE_DRAWS`, тени): фронтенд стал медленнее
   на 0,75 мс — не повторял.
4. **Копии occlusion queries** — не повторная работа: 0,015 мс, батчинг ничего не даст [E].
5. **Отбор света на CPU** — пересчёт каждый кадр по 200–320 источникам; цена в профиле Main не выделяется [E].
   Кэшировать его — изменение логики движка без измеримой выгоды; не делал.

## 4. Оптимизация

### 4.1. Что сделано

| Коммит | Что | Флаг |
|---|---|---|
| `56f65ca` | перепись света (диагностика) + `SSPC_R12_LIGHT_LIST_KEEP`: режим 3 FB-7 — откладывается write-back только списка индексов по тайлам (регистрируется по привязкам tiled CS `0x2edafa400`, 1–64 МиБ, запись); привязки кучи ≥ 256 МиБ не форсируют его write-back; любой другой читатель и любой доступ CPU — форсируют | `SSPC_R12_LIGHT_LIST_KEEP=1` (выкл.), пункт в «Экспериментах» |
| `fffeed0` | диагностика `SSPC_R12_LAZY_TRACE=1`: каждое ожидание CPU отложенного блока — с временем `gpu_frames.csv`, длительностью, адресом и потоком | диагностика |
| `96d916f` | исправление гонки FB-7 (§4.2); `SSPC_FB_LAZY_WB` и `SSPC_REA_HEAP_READS` с числами R12 — на странице «Эксперименты» | — |

Инвалидация (движение источника, камеры, объектов, смена освещения) [A]. Список по тайлам tiled CS пишет
**каждый кадр** заново. Отложенный блок остаётся в видеопамяти — только там он и актуален. Его читают PS через
видеопамять, а в хост он записывается при первом обращении CPU (fault → write-back → показ) или любого
не-кучевого хост-читателя. Поэтому кэша между кадрами нет и инвалидировать нечего: каждый кадр GPU читает свежий
список. Источники не убираются, dispatch/draw/барьеры не пропускаются.

### 4.2. Краш FB-7 и исправление

[E] Два краша в ab4 (Neon Dash, `neon_lazy_3_dirty1` и `neon_rea_all_3`). Картина одинаковая:
- `FATAL guest exception: access violation (protection) nobody resolved`;
- поток JobWorker, `rip eboot+0x3ff6d0`;
- чтение пула частиц `0x26f6dfd8c` / `0x26f90f0ac`;
- на момент записи в журнал защита страницы уже RW;
- за 0,3 с до этого три потока одновременно ждали write-back того же блока `0x26f900000`.

[A] Гонка. Поток A падает на скрытом блоке (`PAGE_NOACCESS`). Поток B, упавший на том же блоке раньше, успевает
записать блок обратно и вызвать `Unhide`: тот снимает бит «скрыт», затем под локом возвращает защиту. Когда
`OnFault` потока A проверяет `IsHidden`, бит уже снят. Ветка чтения возвращала `false` (читатели обычно не
ловятся трекером), и игра падала.

Исправление (только если хоть один блок когда-то был скрыт, то есть только с FB-7): ветка чтения берёт лок трекера.
- Блок снова скрыт → повтор доступа, он уйдёт в путь скрытого блока.
- Страница читаема → повтор чтения.
- Счётчик — «raced and retried» в строке FB-7 файла `gpu_native.txt`.

[E] После исправления (ab6): 14 прогонов Neon Dash с LAZY_WB (12 засчитанных + 2 грязных), крашей 0, `[Error]` 0.
Счётчик гонки во всех 0 — гонка не повторилась. Вероятность пройти 14 прогонов без краша при прежней частоте
(2/11) ≈ 6 %, поэтому это слабое подтверждение (§7).

## 5. A/B

## 6. Корректность

- **Тест отравления** `SSPC_REA_POISON=1`. Хост-копии отложенных блоков и их тени залиты 0xFFFFFFFF, пока их не
  запишет читатель: любой читатель без write-back увидел бы мусор.

  - fight, neon (`check1`), city (`check3`, lazy и rea_all) — картинка цела;
  - `[Error]` 0.
- **Validation + Sync Validation** (`--gpu-native-validate`, `vk_validation.log`):
  - keep в user — 0;
  - rea_all в user и fight (`check2`) — 0 сообщений, слой включён («validation on»);
  - device lost 0.
- **Свечения сквозь стены/заборы** (исправление `146a3bd`):
  - [A] путь occlusion queries флагами не затрагивается. Счётчики пишутся в малые записи DB (`ZpassOnTimeline`, копии
    запросов), их читает CS игры GPU → GPU. Отложенный write-back касается только диапазонов ≥ 1 МиБ, которые шейдеры
    привязывают на запись.
  - [E, частично] В user свечения рисуются только в первые 24–44 с, а экран там чёрный (вход в игру), так что
    сравнивать нечего. В city (traverse, 1,5–12 свечений на кадр в 66–120 с) сняты по 10 кадров в базе, rea_all и
    lazy (`check3`): свечений сквозь стены не видно. Но маршрут расходится, сравнения кадр в кадр нет.
- **TDR / потеря устройства:** System log 05:00–13:06 — `nvlddmkm` 153 и `Display` 4101 нет.
