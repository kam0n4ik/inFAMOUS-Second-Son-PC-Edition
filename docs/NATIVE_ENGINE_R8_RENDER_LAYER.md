# R8-A3: Native Render Layer — рабочий путь движка к CP

Ветка `feature/r8-render-layer` (worktree `E:\SecondSonPC-r7-gbuffer`, от R8.0 `7d1d7c8`), каталог экспериментов
`E:\research\r8\render` (STATUS.md, INTERFACE.md, runs, tools). Адреса — смещения eboot CUSA00004. Статусы —
ANALYZED → GENERATED → OFFLINE_VERIFIED → GAME_VERIFIED → PERFORMANCE_VERIFIED. Метки: [A] анализ кода, [E] измерение.

Задача (ТЗ §5): сделать слой R7 (C3, `SSPC_R7_NATIVE_RENDER=gbuffer`) измеримым рабочим путём, который исполняет
нативные команды **и** уменьшает работу CP; объяснить замерами, почему C3 был медленнее; NR1 — поля команды только по
доказанной нужде; NR2 — ресурсы draw (`R7::Resources::Fill`); NR3 — нативная подача в существующий конвейер; NR4 —
совместимость пробника C3 на `0x14ad0` с `cue_commit` реестра; NR5 — G-буфер / тени по шагам, каждый с verify и
fallback.

## 2. Почему C3 был медленнее (NR3, разбор замеров R7 C5)

Данные — уже снятые прогоны R7 C5 `E:\research\r7\core\runs\r7c5_city_{base,nat}{1,2,3}` (`gpu_native.txt` по

### 2.1 Работа CP та же, меняется только транспорт [E]

| За прогон (base1 → nat1) | base | C3 | |
|---|---|---|---|
| серии / участники серий | 4,31 M / 33,09 M | 4,31 M / 33,06 M | = |
| подготовки стадий (`PrepareStage`) | 18,04 M | 18,20 M | +0,9 % |
| чтения SRT | 817 M | 829 M | +1,5 % |
| SET_SH_REG (0x76) | 215,3 M | 193,3 M | −22 M |
| SET_CONTEXT_REG (0x69) | 96,2 M | 86,7 M | −9,5 M |
| DRAW_INDEX_2 (0x27) | 48,2 M | 41,6 M | −6,6 M |
| DMA_DATA (0x50) | 17,7 M | 15,8 M | −1,9 M |
| токены / операции / записи регистров потока | — | 6,79 M / 12,77 M / 64,6 M | |
| записи очереди CP (`records`) | 40,97 M | 39,25 M | −1,7 M |

C3 убирает ~40 M пакетов PM4, но **те же** регистры пишутся операциями потока (`ApplyNativeRegisters`), и всё, что
после них (`PrepareDraw` → `PrepareStage` → SRT), делается столько же раз. Время CP в нативных операциях —
0,77 мс/кадр (≈ 1775 серий потока за кадр; счётчик `native transport ... time`). Вывод: транспорт сам по себе работу
CP уменьшить не может — нужен **знание движка, позволяющее не делать работу** (§6).

### 2.2 «Участников с меткой материала 3,11 M против 2,48 M» — артефакт [E][A]

Число draw с меткой `kMaterialChanged` одинаково (4,66 M / 4,69 M), серий и участников — тоже. Разница — в отказе
`JoinRun` №16 («другой материал»: 2,82 M base / 3,73 M C3). Причина: нативный commit не пишет предвыборку кода шейдера
в L2 (DMA_DATA, −1,9 M пакетов), а каждый DMA_DATA игры — запись очереди CP, которая **закрывает** открытую серию
(`ParallelCp::BeginRecord`). Без него draw с новым материалом застаёт серию открытой и получает дешёвый ранний отказ 16
вместо «новой серии после закрытия». Работа та же.

### 2.3 −1,57 FPS / +1,7 мс CP — в основном скрытый фактор стенда [E]

Число EVENT_WRITE (0x46) / сливов «timeline write» за прогон гуляет 0,8 k…170 k **в обеих** конфигурациях.
Регрессия по 9 прогонам без C3: CP = 30,08 + 0,89 · (0x46 / 1e5) мс (r = 0,84, остаток sd 0,26 мс). В C5 у nat2/nat3
было 170 k / 115 k, у базы 2 k / 6 k / 42 k. Остатки C3 по регрессии: +0,36 / −0,30 / +2,99 (nat3 — выброс). Собственная
цена C3 ≈ +0,3 мс CP: операции потока дороже пакетов PM4, которые они заменяют (тот же объём записей регистров плюс
разбор операции и `StreamTake`). Подтверждение сэмплером — §5.

### 2.4 «747 k commit — fallback (alt shader)» и `Draw(packet=false)` [A]

- `CheckNativeCommit` → `AltShader` (CUE+0xC1D9/0xC1DA ≠ 0: шейдер ставится `0x6251c0`/`0x625300`) — ≈ 12 % commit
  0x1a1770: игра делает их своим кодом (правильно; ускорения не теряется — их доля работы CP та же).
- Нативный draw идёт в `CommandProcessor::Draw(..., packet=false)`: RunAhead (P6, забегание вперёд по DCB за
  участниками серии) работает только для пакетных draw, т.е. для нативных серий его нет — это тоже часть +0,3 мс.

## 3. NR1 — NativeDrawCommand

В `NativeDrawCommand` новых полей нет. Использованы существующие: `fn` (теперь из области вызова — нужен NR5),
`producer` (Shadows для `0x43d480`), `resources` (заполняется — NR2). В `DrawScope` добавлено `fn` (какая функция
движка открыла область). В `NativeStageResources` (часть `resources`) добавлены по значению `epoch` и `program` —
нужда доказана аудитом A4 (§6.1): без эпохи версия небезопасна как ключ, программу потребитель должен сравнить, а
адрес объекта шейдера — указатель на объект движка.

## 4. NR4 — один вход для `0x14ad0` [A][E]

Проблема R7: пробник C3 (`native_draw.cpp`, `CommitProbe`) ставился **без слота** оригинала, а `cue_commit` реестра
(замена `0x14ad0` на `recomp_14ad0`) при пробнике без слота отказывается ставиться («an entry probe is on it without a
slot») — вместе они не работали и не проверялись.

Решение: пробник ставится со слотом (`InstallEntryProbe(..., &g_commit)`), реестр (ставится после `NativeDraw`,
bootstrap) кладёт свой диспетчер в этот слот (`below_probe`, как `material_bind` под пробником Phase 6). Один вход:
пробник решает — нативный commit в поток (C3/NR5; диспетчер реестра не вызывается) или `g_commit` = диспетчер реестра
(`recomp_14ad0`, verify / guarded / bench по режиму). Двойной обработки нет по построению. Счётчики:
`commit probe calls N, handed below K (native M)` (строка `R8 native render:`), N = K + M.

Другие писатели (аудит A4): участок LCUE `0x5af0…0x11560`, второй commit `0x140d0` и `0x16fb0` в `0x14ad0` не входят
и из него не вызываются — отдельной обработки в диспетчеризации пробника не требуют; их влияние на ресурсы
закрывается на стороне `Fill` (§6.1) и сравнением user data у потребителя.

Проверка: оффлайн — `r8_render_tests.cpp` §1 (пробник со слотом на 0x14ad0 образа, `cue_commit` под ним, все режимы:
нативные вызовы ничего не запускают ниже, переданные — ровно один commit); в игре — §9.

## 6. NR2 — ресурсы draw и знание для CP

`R7::Resources::Fill(cue)` (Native Resource State, R7-R) даёт по (CUE, стадия) binding version: равные версии ⇒
побайтно равный снимок таблицы, та же форма и те же user data. Это то, чего CP не знает (каждый commit — новый адрес
снимка ⇒ промах памятки стадий P4.7 «other user data», 13,2 M за прогон в R7-R).

Проблема для слоя: Native Resource State узнаёт commit, наблюдая вызовы `recomp_14ad0`. Нативный commit слоя
(`NativeCommit`, C3) их не делает ⇒ для draw C3 состояние не знает нового снимка: при изменённом содержимом —
`fills_stale` (стадия не отдаётся), при неизменном — отдаёт **старый адрес** снимка с прежней версией (содержимое то
же, но не тот снимок, что видит CP). Fill для слоя без этого бесполезен.

Сделано (`SSPC_R8_RENDER_RESOURCES=1`, нужен `SSPC_R7_RES_STATE`):
- `R7::ResourceHooks` (`native_render_layer.h`): begin / snapshot / pointer / value / end / fill — header-only
  хранилище указателя (ни одна сторона не линкует другую);
- `NativeCommit` сообщает в хуки те же события, что наблюдатели `recomp_14ad0` (снимок после копии тени, указатели
  `setPointerInUserData`, значения `setUserDataRegion` — в порядке `0x14ad0`), `end` — после сброса dirty-байтов;
- `[shared]` `resource_state.{h,cpp}`: `Commit` разделён на `CommitBegin`/`CommitEnd` (без изменения поведения), новые
  `ExternalBegin/Snapshot/Pointer/Value/End` (тот же учёт), регистрация хуков в `Prepare`, снятие в `Deactivate`,
  счётчик `external_commits`;
- `R7Draw` копирует `Fill` в `NativeDrawCommand::resources` (по значению — безопасно для асинхронной подачи: в очередь
  не попадает ни одного указателя на временный объект).

Проверка: оффлайн — `r8_render_tests.cpp` §2 (случайные последовательности сеттеров / commit игры / нативных commit /
сбросов: после каждого commit присутствующие привязки сверяются с байтами и user data, равные версии = равное
содержимое через оба вида commit, режим verify без нарушений; и обратный тест — без хуков привязка устаревает).

Потенциал для CP (`SSPC_R8_RENDER_BINDINGS=1`, строка `R8 render bindings per frame`): после каждого вызова
`0x1a1960` / `0x43d480` / `0x1a1770` — для VS/PS: новый ли снимок у контекста (промах P4.7 сегодня) и совпадают ли
версия и программа с прошлой (hit1) или одной из 4 последних (hit4) для этой CUE/стадии. Верхняя граница экономии
потребителя в CP. Формат для A2 — `E:\research\r8\render\INTERFACE.md` v3.

### 6.1 Поправки по аудиту жизненного цикла CUE (A4, `feature/r8-recomp` bf1d7b3) [A]

- Версия без эпохи небезопасна: `0x13da0` (каждый кадр в `SubmitFrame`) → `0x12390` поворачивает кольцо снимков; адрес
  снимка возвращается с другими байтами, версия при равных байтах держится. В `NativeStageResources` добавлены по
  значению `epoch` (число сбросов CUE: `0x12390`/`0x13d20`/`Forget`) и `program` (`PGM_LO << 8` стадии; 0 — стадия
  ставится другим путём). Ключ потребителя — `(cue, стадия, version, epoch)` + программа; адрес снимка — только
  проверка «CP читает этот снимок».
- `Fill` не ручается за то, чего не видел: при `fills_stale` стадии нет (как было); новое — курсор аллокатора снимков
  `CUE+0x20` (двигает `0x123d0`, сбрасывает `0x12390`; проверено дизассемблером) сравнивается с запомненным в конце
  наблюдаемого commit; сдвиг (второй commit `0x140d0`, CS-commit между commit и draw) ⇒ ничего не present
  (`fills_moved`). Оффлайн-тест: сдвиг курсора → отказ, следующий commit → снова есть.
- User data потребитель сравнивает по значению (`0x16fb0` пишет SGPR мимо тени).
- Связь записи с draw — через метку Phase 5 в хвостовом NOP (`nop[3]` — индекс в таблицу кадра, бит тега `0x200`),
  без новых PM4-слов; делается, когда будет потребитель.
- Диагностика `SSPC_R8_RENDER_BINDINGS` считает hit1 по тому же ключу (версия + программа + эпоха).

## 7. NR5 — G-буфер / тени через слой

`SSPC_R8_RENDER_PATHS=mesh,shadow` (вместе с `SSPC_R7_NATIVE_RENDER=gbuffer*`): пробники Phase 5 на `0x1a1960`
(одиночный draw прохода мешей) и `0x43d480` (instanced draw теней) открывают область слоя, как `0x1a1770` в C3, с
тегом Phase 5. Внутри — нативный commit и draw (тот же `R7Commit`/`R7Draw`, те же fallback), с `gbuffer-verify` —
`StreamOp::Verify` перед каждым draw (CP сверяет). Композиция с реконструкциями: `gbuffer_mesh_pass` (0x1a2030)
вызывает 0x1a1770/0x1a1960 через их входы в образе — пробники их видят; `shadow_instanced_draw` (0x43d480) ставится
под пробник Phase 5 (слот).
