# Native Render Interface (P5.3B / P5.3C / P5.3D)

Дата: 2026-10-14. [A] анализ eboot, [E] измерено в игре, [H] гипотеза. Опирается на RENDER_ENGINE_ARCHITECTURE.md и
RENDER_ENGINE_PASSES.md.

## 1. Идея: операции движка в командном буфере игры

Второго рендерера нет. Единственный исполнитель — существующий нативный бэкенд SecondSonPC (`--gpu-backend sspc`):
командный процессор (CP) и Vulkan-исполнитель. Описание draw, восстановленное из объектов движка, передаётся в CP
**внутри DCB контекста**, ровно там, где идёт пакет draw игры: это NOP с полезной нагрузкой `"SSPC"`
(`src/engine/render/native_render_ops.h`).

Командные буферы при этом:
- сохраняют порядок, сортировку `SubmitFrame` и переходы состояния;
- отправляются, сцепляются и повторяются как раньше.

CP встречает операцию в той же точке потока, где был бы draw игры. Поэтому порядок относительно смен состояния,
других draw, барьеров (`ACQUIRE_MEM`), EOP-меток и ожиданий остаётся порядком игры **по построению**.

Флаги операции:

| Флаг | Режим | Что делает CP |
|---|---|---|
| `kVerify` | shadow (P5.3B) | запоминает операцию; следующий draw очереди, построенный из PM4, сравнивается с ней; ничего не исполняется дважды |
| `kApply` | нативный (P5.3C) | операция заменяет PM4 своего draw (§4) |

## 2. Что такое «draw движка» (сторона движка, `native_draw.cpp`) [A]

Все draw проходов приходят в две обёртки: `drawIndex 0x623c60(dcb, count, indices, flags)` (из `0x1a1960`,
`0x1a1770`, `0x448b30`, `0x43d480`, `0x5a8f40`) и `drawIndexAuto 0x623a40(dcb, count, flags)` (15 вызывающих).
Обе вызываются сразу после commit CUE `0x14ad0`. Зонд на входе каждой собирает `DrawOp` **только из объектов
движка**, PM4 не читается:

| Поле | Источник в движке |
|---|---|
| проход / sub | `R = dcb − 8`; слот пула → ключ `R+0xDE90/94`; pre −2, post −3, деформация −4; иначе draw не наш (счётчик `foreign`) |
| indexed / число индексов / адрес индексов | аргументы обёртки |
| регистры VS (7) | объект шейдера `CUE+0xC0B0`, блок по `+8`: `PGM_LO, 0, RSRC1 (с модификатором CUE+0xC168), RSRC2, SPI_VS_OUT_CONFIG, SPI_SHADER_POS_FORMAT, PA_CL_VS_OUT_CNTL` — то, что пишет `sceGnmSetVsShader` |
| регистры PS (12) | объект `CUE+0xC0A8`: `PGM_LO, 0, RSRC1, RSRC2, Z_FORMAT, COL_FORMAT, INPUT_ENA, INPUT_ADDR, IN_CONTROL, BARYC_CNTL, DB_SHADER_CONTROL, CB_SHADER_MASK` (`sceGnmSetPsShader350`); нет PS → `PGM 0, DB_SHADER_CONTROL 0, CB_SHADER_MASK 0xF` |
| таблица ресурсов VS/PS | тень стадии `CUE+0x90+stage·0x1800`, первые `layout[0]` dword (сколько commit копирует в снимок), FNV-1a 64; таблица раскладки `CUE+0xC180+stage·8` даёт SGPR-указатели в снимок: байт 7 (начало), 8/9/0xA/0xB (смещения `+0x16/+0x1A/+0x1C/+0x1E`), у VS ещё 5/6 (`+0x18/+0x20`) |

Индекс стадии CUE совпадает с `Gnm::ShaderStage` (1 PS, 2 VS). Если commit задаёт шейдер другим путём (флаги
`CUE+0xC1D9/0xC1DA`), регистры не сравниваются: счётчик `shaders unknown` — за прогоны 0 [E].

Маркер занимает 50 dword. Если места в куске нет, зонд просит его так же, как обёртки игры: колбэк буфера `cb+0x18`
(`0x11eed0`) с запасом под маркер и пакет draw.

## 3. P5.3B: shadow-режим — сверка с PM4-путём и Vulkan-бэкендом

`SSPC_P53_NATIVE_DRAW=shadow` (по умолчанию выключен; `_STATS=<с>` — строка в журнале,
`_CANARY=<n>` — каждый n-й маркер намеренно испорчен). Хеши функций закреплены: обёртки, commit `0x14ad0`,
`AcquireContext 0x1f2c60`.

CP (`command_processor.cpp`, ветка NOP и `Draw`): маркер → ожидание; следующий draw той же очереди → `VerifyDraw`
(`native_render_ops.cpp`) между `DrawOp` и тем, что CP построил из PM4:
- `DrawDescriptor`: вид draw, число индексов, адрес индексов;
- регистры VS/PS из `RegisterFile`;
- user data стадий VS/PS. Каждая SGPR-пара — указатель. Все указатели должны сходиться на одном начале снимка
  (за вычетом смещений), и содержимое снимка в памяти должно давать тот же хеш, что тень движка.

Это проверяет всю цепочку: шейдеры, ресурсы (T#/V#/S#/константы, всё, что видит шейдер через таблицы) и параметры
draw. В Vulkan-исполнитель идёт именно этот `DrawDescriptor`.

**Результаты в игре [E]** (`logs\p53\p53_shadow`, нативный бэкенд, по 90 с):

| Сцена | Draw движка | Сверено | Совпало | Расхождений | Таблиц по содержимому | Контрольные искажения |
|---|---|---|---|---|---|---|
| пляж | 7 962 717 | 7 957 323 | 7 957 323 | **0** | — (счётчик добавлен позже) | — |
| гавань | 9 666 873 | 9 649 532 | 9 649 532 | **0** | 13 233 611 | **9 602 из 9 602 пойманы** |

`foreign` 0, `no space` 0, `malformed` 0, `orphaned` 0. Разница «размечено − сверено» — кадры в полёте на момент
строки журнала. Каждый draw всех проходов, pre/post и деформации описан из объектов движка без потерь, и PM4-путь
доставляет в бэкенд ровно его. Тесты: `sspc_engine_tests` 88/0. Сквозной тест: искусственный кадр → `BuildDrawOp` →
маркер → `VerifyDraw` с верным и испорченным PM4-видом.

Цена: маркер 200 байт на draw, около 0,7 МБ DCB за кадр. FPS shadow-прогонов в пределах обычного разброса
(пляж ср. 31,3 мс, гавань 28,0 мс). Отдельный A/B не проводился, ускорения не заявляется.

Ограничения сверки:
- прямые SGPR (`setUserDataRegion`: одиночные dword `CUE+0xC0E4…`) и указатели вне снимка (`CUE+0x78`,
  `CUE+0xC130`) не сравниваются;
- стадии ES/GS/HS/LS (в этих сценах не включаются) и состояние вне шейдеров (цели, блендинг, viewport) в маркер не
  входят — их по-прежнему задаёт PM4 setup-функций прохода.

## 4. P5.3C: нативный draw — commit CUE и draw без своего PM4

`SSPC_P53_NATIVE_DRAW=apply:<проход>[,<проход>…]` — экспериментальный флаг, по умолчанию выключен. Откат —
не задавать флаг: зонды не ставятся, код игры идёт как раньше. Остальные проходы при этом работают в shadow-режиме §3.

Для контекстов выбранных проходов работают три механизма.

**1. Нативный commit.** Зонд на `0x14ad0`.
- Режим VS/PS (`CUE+0xC1E0 & 0x21 == 0`, шейдеры обычным путём) commit игры не выполняется. `NativeCommit`
  (`native_draw.cpp`) делает то же, что он, без командного буфера:
  - для грязных стадий берёт снимок тени **аллокатором игры** `0x123d0` (порядок и адреса как у игры: VS, потом PS);
  - выдаёт те же записи регистров и в том же порядке: блоки `sceGnmSetVsShader`/`SetPsShader350`, user data
    (указатели в снимок, `CUE+0x78`, `CUE+0xC130`, одиночные dword), `SPI_PS_INPUT_CNTL_n` (значения считает функция
    игры `0x638540` или кэш `CUE+0xC1C0`);
  - сбрасывает флаги CUE так же, как commit.
- Записи уходят в DCB одной операцией `OpKind::Registers` (`kApply`). CP пишет их прямо в `RegisterFile` (через
  журнал параллельного CP), без пакетов `SET_*_REG`.
- В режимах ES/GS, LS/HS и при альтернативном пути шейдеров работает commit игры (счётчики `commit fallbacks`).
- Предвыборка кода шейдера в L2 (`0x623630`, `CP_DMA` без записи) в нативном commit не делается: на результат она не
  влияет.

**2. Нативный draw.** Зонды на `0x623c60`/`0x623a40`.
- Обёртка игры не вызывается, пакета draw в DCB нет. На его месте `DrawOp` с флагами `kApply|kVerify`.
- CP исполняет draw из операции через тот же вход, что пакет: VGT-регистры, `BuildDraw`, `Executor::Draw` —
  с теми же полями, что пишут `sceGnmDrawIndex`/`DrawIndexAuto` драйвера.
- Перед исполнением тот же draw сверяется (§3) с описанием движка. Так каждый нативный draw проверяет результат
  нативного commit: регистры шейдеров и содержимое таблиц ресурсов по указателям user data.
- Если у буфера включена предикация или у обёртки есть флаги, работает обёртка игры (`draw fallbacks`, за прогоны 0).

**3. Порядок, барьеры, синхронизация.** Обе операции стоят в DCB в точке вызова игры. Поэтому порядок относительно
смен состояния, setup-функций прохода, `ACQUIRE_MEM`, EOP и других контекстов — порядок игры. Барьеры и переходы
образов делает тот же Vulkan-исполнитель по тем же правилам, что для PM4-draw.

**Результаты в игре [E]** (нативный бэкенд, по 90 с; `logs\p53\p53_apply*`, `p53_img_*`):

|---|---|---|---|---|---|---|
| пляж, `apply:9`, валидация | 510 | 510 | 11 684 | 0 | 0 из 1,61 млн | **0** |
| пляж, `apply:1,9` | 2 683 430 | 2 116 540 | 19 247 190 | 566 890 | 0 из 8,51 млн | — |
| гавань, `apply:1,9`, валидация | 602 746 | 495 298 | 4 466 208 | 107 448 | 0 из 1,90 млн | **0** |
| пляж, `apply:1,9` + параллельный CP | 3 166 074 | 2 496 901 | 22 739 052 | 669 173 | 0 из 10,05 млн | — |

`processor applied draws` равно числу нативных draw движка (с поправкой на кадры в полёте): каждый нативный draw
исполнен GPU и ни один не потерян.

**Проверка изображения.** Снимки в конце одинакового маршрута (`p53_img_base`, `p53_img_apply9`,
`p53_img_apply1_9`, гавань `p53_apply1_9_val`, параллельный CP `p53_apply1_9_par`): геометрия G-буфера (скалы, песок,
персонаж), освещение, тени и пост-обработка совпадают с базой. Отличаются только поза персонажа и ракурс: кадры
приходятся на разные моменты анимации. Пакеты draw прохода 1 игра больше не пишет, поэтому вся видимая геометрия
G-буфера в этих прогонах отрисована нативным путём. Попиксельного сравнения одного и того же кадра нет:
детерминированного захвата кадра для двух режимов пока нет. Это ограничение.

FPS (ср., без валидации): база 34,4, `apply:9` 31,9, `apply:1,9` 32,6. Это в пределах разброса одиночных прогонов,
A/B не проводился, ускорение не заявляется. Маркеры shadow на всех остальных draw добавляют свою стоимость.

## 5. Ограничения P5.3C (состояние прохода — см. §6)

- **Нативная часть draw** — шейдеры, ресурсы (user data и снимки), входы PS и сам draw. Состояние прохода в P5.3C
  ещё задавали пакеты PM4 игры; в P5.3D оно перенесено (§6).
- **Commit с альтернативным путём шейдеров** (`0x6251c0`/`0x625300`, около 21 % commit прохода 1) и режимы ES/GS,
  LS/HS остаются PM4 игры. Draw после них всё равно нативный и сверяется.
- **Только нативный бэкенд SecondSonPC.** Мост shadPS4 о маркерах не знает. Поэтому `apply` без
  `--gpu-backend sspc` отклоняется при запуске: в журнале ошибка, вместо него работает shadow, а мост пропускает
  маркеры как NOP.
- **Сверка покрывает** регистры шейдеров, таблицы через указатели и параметры draw. Прямые одиночные SGPR сравниваются
  только как записанные значения нативного commit (тест), в игре — нет.
- **Проверены проходы** 1 (G-буфер) и 9 (освещение). Остальные проходы с тем же путём (`0x1a1960`/`0x623a40`)
  включаются флагом, но в игре не проверялись.

## 6. P5.3D: нативное состояние прохода (Native Render State)

`SSPC_P53_NATIVE_STATE=verify|apply` — экспериментальный флаг, по умолчанию выключен; нужен
`SSPC_P53_NATIVE_DRAW` (`apply` — только вместе с `apply:<проходы>` и нативным бэкендом, иначе verify). Код:
`src/engine/render/native_state.{h,cpp}` (вычисление), зонды в `native_draw.cpp`, исполнение в `CommandProcessor::
NativeMarker` (`OpKind::State`).

### 6.1 Что заменено [A]

| Функция игры | Что пишет (PM4) | Нативно |
|---|---|---|
| `0x11f910` SetRenderTargets(R, rtSet, rect) | `ACQUIRE_MEM` при `DAT_00e15e10`; цвет. цели `0x52e0`→`0x622ff0` (14 регистров `CB_COLORn_*` + NOP-подсказка размера; без базы — `CB_COLORn_INFO=0`; FMASK из цветовой поверхности при сжатии без своей FMASK); глубина `0x6230e0` (8+4 регистра `DB_*` + подсказка, либо `DB_Z_INFO=DB_STENCIL_INFO=0`); `0x2DE` (`0x6272e0(3)`); `CB_TARGET_MASK`; вьюпорт `0x11b60` (ZMIN/ZMAX, 6 scale/offset, `PA_CL_VTE_CNTL`, экранный scissor, `PA_SU_HARDWARE_SCREEN_OFFSET`, guard band); оконный scissor по нормализованному прямоугольнику набора; отключение лишних целей прошлого набора; ветка отладочной цели 7 при `DAT_00e171fc` | всё, кроме веток `DAT_00e15e10`/`DAT_00e171fc` (при них — функция игры, счётчик `flags`); float-арифметика вьюпорта и scissor повторяет инструкции SSE игры по одной (без FMA); размеры целей из NOP-подсказок передаются псевдорегистрами `kStateCbExtent0..7`/`kStateDbExtent` — то, что CP берёт в `cb_extent_`/`db_extent_` для Vulkan-исполнителя; R+`0xDE68/0xDE70/0xDE80` обновляются как у игры |
| `0x120020` TransitionTo(R, block) | только регистры блока, разрешённые маской (поле 6) и отличающиеся от R (`+0xDE48..`, биты `+0xDE60`): `PA_SU_SC_MODE_CNTL`, `PA_CL_CLIP_CNTL`, `DB_RENDER_CONTROL`, `PA_CL_VTE_CNTL`, `DB_DEPTH_CONTROL`, `DB_STENCIL_CONTROL` (со своими масками); `DB_STENCILREFMASK(_BF)` при смене; SetRenderTargets при смене набора | то же условно, не безусловная переустановка; блок R обновляется так же |
| `0x11ffe0` SetStateBlock(R, block) | PM4 не пишет: копия блока в R+`0xDE48`, маска целей | не заменяется (нечего), функция игры |
| `0x623740` / `0x624f80` | `VGT_PRIMITIVE_TYPE` (`SET_UCONFIG_REG`), пакет `INDEX_TYPE` | одна запись регистра каждая |
| 15 однопакетных установщиков Gnm (`NativeState::kLeaves`): `0x6270e0`, `0x626e10`, `0x626c60`, `0x626a80`, `0x622bb0`, `0x622c10`, `0x6227e0`, `0x6229a0`, `0x626cc0`, `0x6228a0` (blend), `0x622b30`, `0x627350`/`0x6273c0` (depth bias), `0x6250b0` (`NUM_INSTANCES`), `0x6221a0` | один пакет: регистр и маска | то же значение тем же регистром |

Зачем установщики: после переноса пяти функций в проходе 1 остались пакеты, которые код материалов и мешей пишет
этими функциями напрямую (stencil ref, cull, blend, depth bias, `0xA003`/`0xA293` материала `0x11f3c0`,
`NUM_INSTANCES`) — трасса кадра с новыми счётчиками по регистрам (`frame_trace`: `opcodes`, `context_regs`,
`sh_regs`, `uconfig_regs`, `native_ops` по узлам).

Решение «нативно или игра» — на каждый вызов: контекст известен (R из пула/pre/post/деформации) и его проход в
списке apply → нативно; иначе verify (если включён) или игра. Вложенные вызовы внутри проверяемой функции игры
(`TransitionTo` → `SetRenderTargets` → установщики) считаются частью внешнего вызова. Не исполняемое нативно
(флаги игры, переполнение, нет места) — функция игры (счётчики `fallbacks`).

### 6.2 Проверка корректности [E]

### 6.3 Сравнение изображений (P5.3D.2) [E]

`tools/tests/p53_image_ab.ps1` + `p53_image_compare.py`. Сцена замораживается паузой самой игры (Options на 70 с):
мир рендерится каждый кадр с остановленной симуляцией (одинаковое число draw от кадра к кадру).
`SSPC_P53_NATIVE_AB=4` чередует блоки по 4 кадра: PM4 игры / нативный путь (apply 1,9 + состояние).
`SSPC_P53_CAPTURE_PASSES=1,9` снимает цели прохода там, где начинаются draw следующего прохода (CP по номеру прохода
в маркерах; каждый снимок знает, сколько draw прохода было нативных и сколько PM4), плюс итоговый кадр в конце flip
(`SSPC_DIAG_CAPTURE_IMAGE`, расширен диапазонами и `SSPC_DIAG_CAPTURE_DIR`). Сравнение — побитово и по значениям
(max/MAE/RMS, доля пикселей > 0 / > 1 ед. младшего разряда формата / > 1 %, PSNR; half/float — относительные
пороги; NaN = NaN по битам). Контроль — PM4 против PM4. «Устоявшаяся сцена» — с первого PM4-кадра, после которого
у каждого PM4-кадра цели есть побитовый двойник; цель, которая не устаивается и на PM4, сравнивается с контролем
PM4↔PM4 на том же расстоянии во времени и по пикселям.

| Сцена | Нативных кадров в устоявшейся сцене | Цели | Результат |
|---|---|---|---|
| пляж (`logs\p53\p53d_img_ab_beach`) | 12 (глубины прохода 1 — по 6) | G-буфер 0–4, основная глубина после 1 и после 9, две глубины прохода 1, освещение после 9, итоговый кадр | **все побитово идентичны PM4-кадрам** |
| гавань (`p53d_img_ab_harbour2`) | 21 | основная глубина после 1 и 9, G-буфер 1/3/4, глубины прохода 1, освещение после 9 | **побитово идентичны** |
| гавань | 21 | G-буфер 0 и 2 | **эквивалентность не доказана**: эти цели меняются и между PM4-кадрами (±1 ед. младшего разряда, в G-буфере 0 в основном альфа), нативные отличия тоже только ±1, но на том же расстоянии во времени их местами в 3–6 раз больше, чем PM4↔PM4 (например 23 000 пикселей против 3 967), и 274 / 1 191 пикселя меняются только на нативном пути. Причина не установлена |
| гавань | 20 | итоговый кадр (под меню паузы) | не сравним строго: меню анимируется, PM4↔PM4 тоже различаются |

Первый кадр после переключения и начало окна (сцена ещё досходится — одинаково на обоих путях) исключены правилом
«устоявшейся сцены», а не вручную.

### 6.4 Ограничения

- Заменено состояние, которое пишут перечисленные функции. В проходах 1/9 остаются PM4 игры: `DMA_DATA`
  (загрузки констант), `ACQUIRE_MEM` (барьеры — оставлены намеренно, их порядок — порядок игры), user data вне
  commit, commit с альтернативным путём шейдеров.
- Ветки SetRenderTargets с `ACQUIRE_MEM` (`DAT_00e15e10`) и отладочной целью (`DAT_00e171fc`) не воспроизводятся:
  при этих флагах работает функция игры (в прогонах флаги не встречались: счётчик 0).
- Сравнение изображений — в замороженной паузой сцене (меню поверх итогового кадра); G-буфер 0/2 в гавани не
  доказаны (см. 6.3). Параллельный CP захват по проходам не поддерживает (захваты — только последовательный CP).

## 7. P5.3: прямой путь без маркеров (`SSPC_P53_DIRECT=1`)

### 7.1 Что несут маркеры и какие гарантии порядка дают [A]

| Маркер | Сколько | Данные | Кому нужны данные | Гарантия порядка |
|---|---|---|---|---|
| `Draw` + `kDescribe` | каждый draw вне проходов 1/9 (HYBRID) | 50 dword: проход, регистры VS/PS, index count/base, две таблицы стадий (размер, FNV-хеш содержимого, ссылки SGPR→смещение) | фронтенду — только проход и ссылки/размер таблиц; хеш и регистры — только проверке (`kVerify`) | привязка к **следующему** пакету draw очереди |
| `Registers` (`kApply`) | каждый нативный commit CUE | записи регистров (указатели user data на снимки, регистры шейдеров, `SPI_PS_INPUT_CNTL`) | регистровому файлу CP | место commit в потоке: до draw, после пакетов игры перед ним |
| `State` (`kApply`) | каждая нативная смена состояния | записи регистров состояния + размеры целей | регистровому файлу CP | место метода игры в потоке |
| `Draw` + `kApply` | каждый нативный draw | draw (вместо пакета игры) + описание | исполнителю, фронтенду | место draw в потоке |

Порядок гарантирует не содержимое маркера, а **его место в DCB**. Один и тот же регистровый файл CP пишут и
нативные операции, и PM4 игры, которая осталась в проходах 1/9 (§6.4): `DMA_DATA`, `ACQUIRE_MEM`, user data вне
commit, commit альтернативных шейдеров. Барьеры и метки — тоже пакеты этого потока. Порядок DCB разных контекстов
задаёт игра при отправке (`SubmitFrame` сортирует контексты). Поэтому операции, вынесенные из потока совсем,
потеряли бы своё место относительно пакетов игры. Это конкретная архитектурная зависимость: **позиция нужна, данные
в потоке — нет**.

### 7.2 Прямой путь [A]

- **Описание draw — 0 лишних пакетов и dword.** `sceGnmDrawIndex`/`DrawIndexAuto` пишут после draw NOP из 4 dword, тело
  которого железо не читает (драйвер обнуляет только первое слово). Движок после обёртки игры пишет туда
  `kDescribeMagic`, проход и id форм таблиц VS/PS. Формы интернируются один раз на уникальную раскладку
  (`InternShape`); хеш содержимого не считается — он нужен только проверке. CP читает NOP в `Draw()`, когда берёт
  draw.
- **Операции проходов 1/9 — нативный поток.** Commit, состояние и draw пишутся готовыми к исполнению в блоки памяти
  SecondSonPC (`StreamReserve/StreamCommit`: 2048 блоков по 16 КиБ, у контекста свой курсор). В DCB — один токен из
  4 dword на **серию** операций: следующая операция дописывается в открытую серию, если указатель записи DCB с тех пор
  не сдвинулся (значит, пакетов игры между ними нет). CP на токене исполняет серию по порядку (`NativeRun`): регистры,
  состояние, draw через тот же `Draw()`. GPU flush и ожиданий CPU нет — место токена и есть порядок.
- **Безопасность.**
  - CP «забирает» серию атомарно: бит taken ставится через `fetch_or`, а движок дописывает через CAS. Операция после
    забора начинает свою серию и не теряется.
  - Повтор того же токена и токен на переиспользованный блок (поколение блока) ничего не исполняют и считаются.
  - Нет места в DCB или свободного блока — работает путь игры (fallback до любых побочных эффектов: commit
    резервирует место до `NativeCommit`).
  - Проверка (`kVerify`) остаётся на маркерах: это проверка, а не горячий путь.
