## 2. Smoke Quality

### Как работает

Число частиц уменьшается в самой системе эффектов игры — при рождении, до симуляции и отрисовки; проход
рендера, шейдеры и прочие эффекты не трогаются.

- Проба на `EmitterSpawn` **`0x3f3580`** (хеш тела `{0x3f3580, 0x7a7, 0x91c01916f8965f17}`, пролог 20 байт):
  вызывает оригинал, затем у эмиттеров дыма масштабирует прирост `emitter+0x78` (число новых частиц кадра) с
  дробным остатком на эмиттер (`ScaleSpawn`); при флаге 4 — и общий счётчик `data+0x164`; интервал рождения
  `+0x80` растягивается, чтобы оставшиеся частицы шли по тому же времени. Эмиттер без живых частиц получает
  минимум одну — эффект не исчезает.
- Проверяемые соседние функции: вызывающий `0x3f3280` (`{0x2f9, 0xafefbaab910557e4}`), `EmitterUpdate`
  `0x3efde0` (`{0xb01, 0x4274811e7ad63eb6}`) — переносит `+0x78` в константы GPU-dispatch (`*(e+0xe8)+4`).
  При несовпадении любого хеша проба не ставится, игра идёт с оригинальной плотностью.
- Дочерние эмиттеры уменьшенного родителя повторно не уменьшаются (`data+0x108` — родитель).
- **Какой эмиттер — дым:** по имени. `data+0x18` — хеш имени движка `h = h·101 + lower(c) mod 2^64`; короткие
  имена восстанавливаются перебором переполнений, длинные — по словарю составных «smoke»-имён; дым = имя содержит
  `smoke`. Деревня: `smoke`, `smoke01`, `thick_smoke`, `smoke_near` — дым; `flames_small`, `flames_large_inner`,
  `light_fire`, `embers` — огонь (не трогается). Пляж: `thick_steam`, `thin_steam`, `dust*`, `foam_*` — не дым.
- Урон, физика, коллизии, события и звук не затрагиваются: проба пишет только счётчики рождения, которые читает
  лишь `EmitterUpdate` для размера GPU-dispatch (проверено по дизассемблеру вызывающих мест).
- Настройка `[Graphics] smokeQuality = high|medium|low|verylow` (меню F1, применяется на лету), по умолчанию
  `high` = оригинал (проба вызывает оригинал без изменений). Переменная `SSPC_SMOKE_QUALITY` перекрывает для тестов.

## 3. Particle Resolution

Родной механизм движка: `TranslucentParticles` **`0x3ed7b0`** (`{0x2ef, 0x1de2d1e52e4cf14e}`, пролог 17)
выбирает уровень менеджера частиц (`eboot+0x7d3eb10`, поле `+0xca0`: 0/1/2) по GPU-таймерам PS4; уровень ≥ 1
переносит технику `particle_translucent` в проход 28 (`0x1923f0`, цель = экран × {1, 0,5, 0,25} из `0xaaa918`,
апскейл в `0x1926e0`). Таймеры порта не дают значений PS4, поэтому уровень всегда 0; настройка
`[Graphics] particleResolution = auto|full|half|quarter` (по умолчанию `auto` = поведение игры) пишет уровень
перед каждым вызовом. Возврат в `auto` восстанавливает стартовый уровень 0.

Проверено профайлером: draw огня (VS `0x2edac4000`) 1920×1080 → 960×540, 2,16 → 0,62 мс.

## 4. Async compute: проверка гипотезы

### Шаг 1. Очереди Vulkan

`vulkaninfo` (RTX 2060): семейство 0 — graphics+compute+transfer ×16, 1 — transfer ×2, **2 — compute+transfer ×8**,
метки времени 64 бита. Бэкенд использует одну `VkQueue` (`vk_device_context.h`): все гостевые очереди
записываются в один поток команд в порядке процессора команд.

### Шаг 2. Таймлайн очереди 1 (трасса `SSPC_DIAG_CMD_TRACE`, серия `trace1`)

- На кадр: очередь 0 — ~5580 draw + 154 dispatch; очередь 1 — 1233–1448 dispatch (1×1×1) в 5–6 блоках, до 292
  подряд; 222 разных программы, одна программа подряд почти не повторяется.
- Каждый dispatch пишет в общий пул частиц (привязка ~12–13 МБ) — объединить их в один dispatch без
  переписывания шейдеров нельзя (цепочек одной программы без конфликта — 0).
- **Зависимостей между очередями внутри кадра — 0**: графика читает данные прошлого кадра.
- Барьеры перед dispatch очереди 1 (~430/кадр без блочной загрузки): RAW 152–262 — их требует сама игра
  (между зависимыми dispatch она делает flush очереди); без конфликта 111–237 — барьеры загрузок и теневых копий.

### Шаг 3. Разбивка времени

| источник | что показывает | GPU мс/кадр |
|---|---|---:|
| полный профайлер (`SSPC_GPU_PROFILE=1`) | ~1510 dispatch очереди 1 ≈ 20 мс | завышено: метка после каждой команды сериализует GPU |
| `brk1`: base → без симуляции частиц | вся система частиц (dispatch + их барьеры/загрузки + обратные копии) | 28,3 → 14,6 = **13,7** |
| `brk1`: блочная загрузка → без симуляции | то же с блочной загрузкой | 21,1 → 14,5 = **6,6** |
| профиль по очередям (`SSPC_GPU_PROFILE=q`, серии `qprof1`/`qprof1b`), base, 2 прогона | блоки очереди 1 целиком (dispatch, барьеры, загрузки, тени) | **9,18 / 9,90** |
| там же, блочная загрузка, 2 прогона | то же | **3,00 / 2,98** |
| там же, base / блочная | обратные копии записей GPU в память хоста (конец батча) | 3,4–3,6 / 3,6 |
| там же, base / блочная | очередь 0 (графика) | 13,8–15,1 / 14,0–14,5 |

Метки времени профиля по очередям — только на смене гостевой очереди и в конце батча (~28 на кадр против ~7000 у
полного профайлера), поэтому GPU почти не сериализуется: сумма 26,4 / 20,6 мс совпадает с GPU-временем обычных
прогонов (28,3 / 21,1).

Половина стоимости частиц без блочной загрузки — синхронизация (барьер перед каждой загрузкой опустошает весь GPU),
а не вычисления: блочная загрузка снимает ~7 мс, и только у частиц (без частиц она ничего не меняет:
14,6 → 14,5). На CPU каждый из ~1000 dispatch симуляции стоит потоку записи ~4,4 мкс (≈ 4,4 мс CP/кадр).

### Шаг 4. Решение

Async compute мог бы перекрыть с графикой не больше 3,0 мс GPU (блоки очереди 1). После блочной загрузки GPU
занят ~21 мс, а CP 25–29 мс — кадр ограничивает CPU, длинные кадры совпадают со всплесками CP. Обратные копии
результатов симуляции в память хоста (игра читает счётчики живых частиц) — синхронная точка, которую вторая
очередь не убирает. По условию ТЗ («не создавай вторую очередь ради галочки») вторая очередь не делалась.
Пакетирование dispatch в один невозможно без переписывания шейдеров (222 программы, общий пул 12 МБ); реальный
рычаг на CPU — стоимость записи одного dispatch (~4,4 мкс).

## 8. Блочная загрузка по умолчанию

`vk_buffer_cache.cpp`: первая недостающая страница блока подтягивает остальные использованные и устаревшие страницы
того же блока одной загрузкой — вместо отдельной загрузки и барьера на каждую привязку. Обоснование: очередь 1
9,2 → 3,0 мс GPU, FPS 26,4 → 31,3, кадров ≤ 36 мс 4–51 % → 79–87 % (`blk1`), Validation + Sync Validation 0
сообщений (`val2`), способности и эффекты без отличий (`abil1`). В лог пишется «block upload on»; при
`SSPC_P49_BLOCK_UPLOAD=0` — предупреждение и поведение P4.8.

## 10. Система частиц движка (Ghidra) и что дальше

- Менеджер частиц `eboot+0x7d3eb10`: `+0xc00` — счётчик/минимальный приоритет кадра, `+0xc08` — порог,
  `+0xc0c` — бюджет (`0x3ef180`); `+0xca0` — уровень разрешения (раздел 3).
- Кадр менеджера `0x3ee7d0` (из `0x29c8d0`): лимит эмиттеров `DAT_00df886c = 2000` (переопределения в списке
  `DAT_07d3fa58`), при превышении отсекаются самые старые. В деревне ~950 — лимит не срабатывает. Понизить его
  можно, но это убирает огни — визуальная потеря, по ТЗ не делалось.
- `0x3f3280` — обход эмиттера: затухание, бюджет, список обновления `DAT_07d3edc0/edc8`, звук `0x3f3d40`, спавн
  `0x3f3580`.
- `EmitterUpdate 0x3efde0`: эмиттер без живых и новых частиц пропускается целиком; иначе каждый кадр выделяет
  вершины/данные под все живые частицы из кольца кадра (`DAT_07d3eb20/28`, общий лимит частиц `0x20000`),
  выдаёт dispatch рождения (`0x169f60`) при новых частицах и ставит эмиттер в список симуляции
  `DAT_07d3edd0/edd8` (симуляция — `0x3f09a0`).
- Отсюда: **пропускать кадры симуляции хуком нельзя** — вершины текущего кадра пишет только симуляция, без неё
  частицы мигают/пропадают (это и видно в диагностике `skip`). Число dispatch ≈ число активных эмиттеров, не
  частиц, поэтому Smoke Quality почти не меняет FPS.
- Рычаги по убыванию отдачи: (1) своя нативная система частиц — один пакетный dispatch на тип вместо ~950 по
  одному эмиттеру; нужен разбор VM выражений `0x3f4060` и 222 sim-шейдеров; (2) нативный рендер вместо трансляции
  PM4 (P5) — убирает поток записи как класс; (3) микрооптимизации потока записи — 10–20 % CP.
