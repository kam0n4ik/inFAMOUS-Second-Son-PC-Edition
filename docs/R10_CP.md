## 2. Этап 2: что реализовано

### 2.1. `SSPC_R10_NATIVE_DRAWS` — подготовка теней и меша из состояния CUE

- [A] Пробы движка на 0x1a1960 и 0x43d480 (`draw_runs.cpp`, CITY-OPT) после оригинального вызова снимают теневые копии
  стадий CUE (VS=2, PS=1; `GDR::CaptureStage`, шаблон `StageShadowOf<N>`, компактная ёмкость 224 dword — максимум в
  городе 216) в своё кольцо (32 768 слотов, seqlock), ставят `kNativeDesc` в трейлинг-NOP и номер слота в nop[3].
- Фронтенд готовит такие draw механизмом `NativeGBuffer` (отдельный экземпляр на источник; `ShadowRef` — вид на захват
  любой ёмкости): шаблон по ключу (программы, pipeline, targets, layouts), планы стадий из карт стадий, вариант
  модулей; режимы verify (обе подготовки, используется полная), guarded (каждая 64-я проверяется, при расхождении путь
  выключается), native.
- Отключено по умолчанию, предупреждение EXPERIMENT в логе.

### 2.2. `SSPC_R10_RUN_PS` — члены run меша/теней со своим PS

- [E] Счётчики отказов run по группам (теперь для всех источников): run меша заканчивались на группе PsUserData
  (915 711 за прогон city fight, ~133/кадр), теней — 499 527 (~73/кадр), остальные группы — DepthBounds/DepthStencil/
  Raster (~120 тыс.).
- [A] С флагом такой draw присоединяется к run, как член run G-буфера (Phase 6): его PS-план разбирается заново
  (RedecodeStage), отличаться могут только константные блоки (свои дескрипторы) и, с `_MATERIAL=1`, T#/S# (механизм
  `SSPC_CITY_GB_RUN_MATERIAL`). На T2 член пишется `DrawRunMembers` (свои буферы/образы поверх дескрипторов run) или,
  если «lean» нельзя, полным `RecordDraw` со своими видами. Stencil ref по-прежнему заканчивает run.

### 2.3. Диагностика

- `SSPC_R10_T2_PARTS=shadow|mesh|untagged`: секции R8 «T2 G-buffer record: …» и «T2 BindStage G-buffer: …» считают
  записи этого источника (в отчёте строка-пояснение).
- gpu_native.txt: «R8/R10 <источник> members refused for registers (3), by group», «R10 mesh / shadow members with a PS
  of their own», «R10 engine captures (...): made, not captured, game threads X ms», отчёты NativeGBuffer по источнику;
  лог verify называет первую отличающуюся вершинную привязку.

## 5. Новое узкое место

Не сдвинулось: запись T2 (~16,9 мс busy в городе) и кольцо T1 → T2 (T1 ждёт 8–9 мс/кадр). В city fight кроме того
T1 ~3,3 мс ждёт GPU (compute C1, работа pacing). Содержательных «лишних» работ на draw, которые можно убрать данными
движка без потери корректности, по профилю почти не осталось: дорогая часть записи — команды Vulkan (~0,7 мкс/draw),
BindStage с состоянием образов (~1–1,5 мкс на стадию) и pipeline/vertex/барьеры (~0,2–0,3 мкс каждая) — это
стоимость самой записи. Сокращение T2 — распараллеливание записи (отдельные command buffers / воркеры) — зона sched.
