### 3.3 CP: кто из двух тратит 1,66 мс [A по числу команд, E по командам]

- Проход мокроты 0x597ec0 на CP — **3 команды** на кадр (1 draw + 2 dispatch, cs 0x2edaa2f00 ×9 — это 11).
  При ~1,3–1,6 мкс на команду это < 0,02 мс.
- Карты теней дождя (виды Rain / Rain Dynamic, 0x43c350 / 0x43fcb0 по анализу weather) — **~995 (user) / ~1205
  (rainday) depth-only draw на кадр**, 427 instanced, 1,15 млн индексов, 16,8 тыс. пакетов PM4 и 267 КБ командного
  потока на кадр (кадр трассы 15000, «pass 1» 2282 → 1291 draw). GPU у них дешёвый (0,15–0,2 мс), а CP платит за
  каждую команду. 1,66 мс / ~1040–1250 команд ≈ 1,3–1,6 мкс на draw — обычная цена команды в нашем CP.
  **Итого: CP-часть цены мокроты ≈ 99 % — тени дождя.**
- Обе 1024²-карты получают в среднем по ~498 (user) / ~552–603 (rainday) draw на кадр; в двух кадрах трассы
  (14000, 15000 — оба чётные) в целях виден только 0x304a20000 → вероятно, карты чередуются кадр через кадр
  (двойная буферизация) [H] — тогда повторной отрисовки одного и того же в две карты в одном кадре **нет**.
- **Для lights**: цель глубины 0x304a20000 в user — общая с «проходом 28» (0x1923f0..0x1926e0, 30–63 draw);
  проход 28 тоже исчезает при dry (2/2 кадров трассы). Мой старый ярлык gpass «spot shadow atlas 1024 (pass 28)»
  ставился по размеру цели и был неверным — в user эта цель почти целиком тени дождя.

Кандидаты на ускорение кодом при той же картинке (не сделаны, см. «Не проверено»):
1. CP-цена серии из ~1000 depth-only draw с одним pipeline (меняются user data VS 0x2c4c..0x2c53 и индексы) —
   быстрый путь CP/T2 для «того же состояния»; это общая работа CP (R10/R11), не погодная, объём большой.
2. cs 0x2edacfd00 — 0,36 мс одним запуском в дождь: проверить, нет ли той же эмуляции exec в цикле, что у
   0x2edaa0c00 (метод §4 переносится).
3. Композит +0,25 мс на мокром — ветка шейдера с отражениями (refl).

## 4. Ускорение: сортировка частиц `SSPC_R12_PSORT` (тип A, та же картинка)

### 4.1 Что это за шейдер [A]

compute 0x2edaa0c00 (очередь q1, 1×1×1 группа на эмиттер, 64 линии) — **ранжирование записей пула частиц**:

- ключ записи — слово +0x1c (hi = key>>20 со знаком, lo = key & 0xFFFFF), шаг записей — из слова 1 V# (биты 16..29);
- каждая линия проходит **по всем записям эмиттера** [base, end) и считает: сколько hi меньше / равно, сколько lo
  меньше при равном hi (ранг = их сумма), соседей сверху/снизу (наследник/предшественник с переносом по биту 19);
- пишет запись в end + ранг, добавляет пару (расстояние, адрес) в список (binding 4) через subgroupElect +
  atomicAdd (binding 6) + ExclusiveBitCount.

Транслятор (GCN → SPIR-V) честно эмулирует маску exec консоли: каждая итерация цикла = ballot / InverseBallot на
каждую ветку, ~40 зависимых операций на шаг. В сейве владельца (`user`, candy) 80 запусков за кадр по ~100 мкс —
[E] 8,5 мс сериализованного GPU-времени на кадр (в бою/дневном городе 0,03–0,33 мс). Это не свет и не мокрота:
частицы (дым, пар, капли) у воды на закате.

### 4.2 Что сделано [A]

`tools\r12\psort_patch.py` патчит **собственную трансляцию** шейдера (SPIR-V-ассемблер, якоря — точные id дампа
`shader_2edaa0c00_ef4c6428ecbe8d94.spv`): перед исходным циклом вставлен эквивалентный цикл без эмуляции exec —

- его выполняют все линии (варп не расходится), обновления маскированы исходным exec (%73);
- 4 ключа за шаг, загрузки с ограничением `UMin(j+k, end-1)`, те же сравнения в том же порядке, те же формулы;
- результат записывается в те же регистры (%272–275, %141, %143, %221), а счётчик исходного цикла — в его конец
  (`%147 = %261`): исходный цикл сразу выходит, всё дальнейшее (запись записи, добавление в список) — исходный код.

Генерация: `py -I tools\r12\psort_patch.py --header <дамп.spv> src\runtime\gpu\vulkan\vk_r12_psort_spv.h`
(spirv-dis → патч → spirv-as → spirv-val). В исполнителе (`Executor::PsortVariant`, `vk_executor.cpp`) модуль
подменяется **только** при точном совпадении SPIR-V (7110 слов и FNV-1a 0x976640fd391c29d1); любая другая
трансляция — как есть (строка в журнале). Вариант — временный модуль (id ≥ 0x60000000, не в манифесте прекомпиляции),
привязки и план — исходные. Флаг `SSPC_R12_PSORT=1`, выключен; пункт «Быстрая сортировка частиц (R12)» в
«Экспериментах» (группа «Частицы и погода (R12)»).

### 4.3 Эквивалентность [E]

Стенд-харнесс `E:\research\r12\runs\wfx\harness\psort_harness.cpp` (Vulkan на RTX 2060, subgroup 32): 7 буферов по
4 МиБ, push 72 байта, случайные пулы с уникальными и с повторяющимися ключами, сравнение каждого слова (список
binding 4 — как мультимножество), отладочные выгрузки регистров цикла (`dbg_insert.py`).

| проверка | результат |
|---|---|
| регистры цикла каждой линии (ранги, счётчики, соседи), уникальные и повторные ключи | **200/200 бит-в-бит**, расхождений в отладочной области 0 |
| записи пула, уникальные ключи | бит-в-бит |
| список (binding 4), уникальные ключи | оригинал против самого себя расходится в 1/50 прогонов, вариант против оригинала — в 2–7/50 при равном числе записанных слов |

## Не проверено

- PSORT: neon (1 пара, большой разброс погони/перезагрузок чекпойнта), бой (fight) и пляж — не сняты; длительный
  soak с PSORT; повтор A/B без фоновой нагрузки владельца (все пары ab1 после 13:58 под браузером).
- PSORT: картинка проверена харнессом (регистры), не попиксельным сравнением кадров игры (частицы анимированы, шум
  окна 7–8). Повторяющиеся ключи частиц: и оригинал, и вариант дают гонку записи (как на консоли/в трансляции),
