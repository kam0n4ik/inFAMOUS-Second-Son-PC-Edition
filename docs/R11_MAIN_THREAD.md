# R11 main — главный поток игры (guest:Game:Main)

Ветка `feature/r11-main` (worktree `E:\SecondSonPC-r10-cp`, база `24984ed`). Данные: `E:\research\r11\runs\main\`.
Метки: [E] — измерено, [A] — по коду/дизассемблеру, [H] — гипотеза.

## 1. Как мерили

- **Пресет R11.** Стендовый пресет r9run (CP native, CITY_PERFORMANCE, REA_MERGE_RUNS, ROUND_NODRAIN=1, ASYNC_ACQUIRE,
  ASYNC_PIPELINES, P53 frontend, async writes/flip, emit thread/batch, ring 128, NATIVE_GBUFFER) плюс
  `SSPC_R9_PCACHE=1; SSPC_R9_HEAP_WINDOW=1; SSPC_R10_AJM=native; SSPC_R10_SYSRT=native`.
- **Сцены:**
  - бой — `-Scene city -Route fight`;
  - тяжёлый сейв — `-Scene user -Route calm`;
  - Neon Dash — `-Scene neon -Route neon`.
- **Профиль.** `SSPC_R9_GPROF=2` (стеки, rip гостя), разбор — `tools/r11/main_split.py`.
  - Каждый сэмпл Game:Main относится к одному из классов:
    - «игра» — rip в eboot, вне ожиданий;
    - «наши» — rip в SecondSonPC/shadPS4/ntdll по вызову из eboot;
    - «ожидание» — спин delay `0x53b2b0`, вызванный из ожидания compute `0x1695e0` (callers `0x3edef0` = cw_emitters,
      `0x3ee470` = cw_light), или из EOP-ожидания SubmitFrame (`0x1f2705`);
    - «jobwait» — delay из WaitBatch `0x243c50`;
    - «blocked» — поток не на CPU.
  - Классы и адреса проверены дизассемблером (`tools/r11/dis.py`, capstone по образу `tools/ps4elf.py`).
- **Трасса.** `SSPC_P412_STALL_TRACE=deep,window=80:92,sample=0` + `SSPC_P54_FRAME_TRACE=1`.
  - `tools/r11/cc_chain.py` разбивает каждое заблокированное ожидание compute на этапы, времена GPU — по calibrated
    timestamps.
  - `tools/r11/label_path.py` раскладывает отрезок «GPU end → метка» на две части: «completion увидел Poll» и «метку
    записал CP», и показывает, кто что делал на T1 внутри этого отрезка.

|---|---|---|---|---|

| CP → отправлено | 0,30 | 0,25 | 0,28 | — |
| отправлено → старт на GPU | 0,95 | 3,30 | 4,98 | **neon**: compute в очереди за графикой (main-очередь) |
| исполнение на GPU | 1,81 | 1,72 | 3,06 | GPU |
| **GPU end → метка записана** | **0,90** | **0,88** | **1,10** | **наше (main)** |
| метка → игра проснулась | 0,025 | — | — | — |
| ожидание целиком | 7,95 | 11,68 | 14,64 | |

Заблокированных ожиданий на 12-секундное окно трассы: бой 725, сейв 690, Neon 580 — около 1,3 на кадр.

**Разбор «GPU end → метка»** (`label_path.py`, бой):

- 0,46 мс проходит, пока Poll увидит completion. Видят его T2 (Record) — 634 раза, и T1 (CP) — 91 раз. При CP-9 NODRAIN
  T2 делает Poll только на RoundEnd и fence-записях.
- Ещё 0,44 мс проходит, пока T1 запишет метку. T1 применяет отложенные completions (`ApplyCompletions` →
  `CompleteWork` → `WriteFence`) только между слайсами очередей. Внутри этого отрезка T1 занят CpQueueSlice
  (0,87 мс) и QueueFull (0,38 мс).
- Метку всегда пишет CP.

Это наш сегмент, и он единственный на пути, который чинится без изменения порядка работы GPU.

Причины, переданные другим агентам (через SHARED_NOTES, 03:35):
- «CP дошёл до RELEASE_MEM» — агенту **t2**;
- «отправлено → старт на GPU» — агенту **neon** (AQ и разрезы compute-очереди).

## 4. Что сделано (за флагами, по умолчанию выключено)

### SSPC_R11_FAST_LABEL=1 — коммит `3d886c6`

Требует CP-9 (`SSPC_CP_ROUND_NODRAIN=1`, он есть в play.cmd). Без NODRAIN флаг ничего не делает.

- **T2** (`ParallelCp::Loop`): после каждой записи, не чаще чем раз в `SSPC_R11_FAST_LABEL_US` (по умолчанию 100 мкс,
  допустимо 10..10000), вызывает `Executor::PollIfCompleted()`:
  - один запрос timeline-семафора;
  - если старший батч в полёте завершён, выполняет обычный `Poll()` на том же потоке, где и раньше (поток
    исполнителя).
  - с AQ запрос не делается: сразу вызывается `Poll()`, он сам разбирает lane-батчи.
- **T1** (`NativeBackend`, цикл пакетов): после `cp_->Step(q)` == Packet, если `executor_->CompletionsReady()`,
  вызывается `ApplyCompletions()`. Это та же функция, что и между слайсами, теперь ещё и между пакетами.
- Счётчики в `gpu_native.txt`: «R11 fast labels: recording thread polls that collected N, completions applied between
  packets M». Бой: 89–93 тыс. / 98–102 тыс. за прогон.

### SSPC_R11_LABEL_WAIT=1 — коммит `537d531`

Ожидание compute игры спит на метке вместо спина delay(50) без PAUSE.

- Ставит хук на `0x1695e0` через существующий `ComputeWaitHook`; адреса `kComputeWait` и `kDelay` проверяются.
- `LabelWait::Sleep` (`src/runtime/gpu/r11/label_wait.*`):
  1. спин с `_mm_pause` до `SSPC_R11_LABEL_WAIT_SPIN_US` (по умолчанию 20 мкс);
  2. затем `WaitOnAddress` на метке, таймаут 1 мс.
- `CommandProcessor::WriteFence` после записи вызывает `LabelWait::Written`. Если адрес ждущего попадает в
  `[addr, addr+bytes)`, будит его через `WakeByAddressAll`.
- Порядок Dekker:
  - ждущий публикует адрес (seq_cst), затем перечитывает метку;
  - писатель записывает метку, ставит seq_cst-fence, затем читает адрес ждущего.

## 5. Эквивалентность и безопасность [A]

Замены функций нет: оба флага меняют только **когда** выполняется существующий код. Поэтому verify-режима
«сравнить результат» здесь нет. Вместо него проверено следующее.

**FAST_LABEL**

- `Poll()` и `ApplyCompletions()` — те же функции, на тех же потоках, в том же порядке (completions идут FIFO).
  Меняется только момент вызова.
- Запись метки раньше, между пакетами, эквивалентна асинхронной EOP-записи на PS4: там метка тоже появляется в любой
  момент относительно исполнения CP.
- `PollIfCompleted` без AQ не трогает состояние, если старший батч не завершён.

**LABEL_WAIT**

- Пропущенное пробуждение ограничено таймаутом 1 мс. После каждого пробуждения или таймаута метка проверяется заново
  тем же условием, что у игры: u32 `<`, как `jb`.
- В логах сейчас «ended by the 1 ms timeout» — около 20 % снов.
  - Это ожидания длиннее 1 мс: метка за это время не менялась, поток засыпает снова.
  - Отличить их от пропущенного пробуждения по счётчику нельзя [H].
  - Трасса tf_both: «метка → игра проснулась» 0,001 мс (n 814), то есть пробуждение по записи срабатывает.
- Счётчики логируются на 1/100/1000/10000 ожиданиях. До 100000 прогоны не доходят, поэтому итоговых счётчиков по
  геймплею нет.

**Все 30 A/B-прогонов:** 0 device lost / [Critical] / [Error], P412-трассы без ошибок.

Визуально в игре не проверено — **NOT TESTED**.

## 9. NOT TESTED и риски

- **Не проверено в игре** визуально: артефакты, порядок эффектов. Оба флага.
- **FAST_LABEL:**
  - `Poll()` на T2 чаще — до раза в 100 мкс, только когда батч завершён (~90 тыс. за прогон).
  - Если когда-нибудь Poll станет дорогим, вырастет T2. Сейчас T2 не критичен (вывод t2).
- **FAST_LABEL + AQ:** `PollIfCompleted` с AQ вызывает Poll без предпроверки. С AQ (Neon у агента neon) не мерили.
- **LABEL_WAIT:**
  - адрес ждущего один, глобальный (`g_waiter`). Он рассчитан на один поток, ждущий через `0x1695e0`, — это Game:Main;
  - второй одновременный ждущий получил бы только таймаут 1 мс [A];
  - итоговые счётчики снов за геймплей не логируются (см. раздел 5).
- **EOP-ожидание** SubmitFrame (`0x1f2705` → `0x1f270a`, 2,9 мс в бою и 9 мс в спокойной фазе) не трогали. Это
  ожидание GPU-кадра, сон его не сократил бы; полезна была бы разве что экономия SMT-соседа [H] — без доказательств
  не делали.
- **Neon** очень шумный: n = 6 при разбросе ±10 %. Выводы по Neon — только направление.
