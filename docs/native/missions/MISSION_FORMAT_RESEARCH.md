# Система миссий inFAMOUS Second Son: что установлено (N12)

Метки: **[П]** подтверждено на данных и/или в коде eboot; **[A]** прочитано в коде eboot (Ghidra, только чтение);
**[Г]** гипотеза; **[?]** неизвестно. Образцы: `E:\shdps4\CUSA00004\art\cache`. Исследовательские скрипты:
`native/tools/research/missions/` (`ebootimg.py` — образ eboot и хеш имён, `objects.py` — каталог объектов,
`dump.py` — аннотированный дамп, `plps.py` — линковка скриптов, `gen_type_table.py` — таблица типов).
Образ eboot выгружен из проекта Ghidra в `native/build/eboot_image/` (в репозиторий не входит).

## 1. Хеш имён движка [П]

`h = h·101 + lower(c)`, 64 бита с переполнением (`core/name_hash.h`). Доказательства:
* словарь eboot `0xa5ff70` (`{u64 хеш, u64 значение}` × 7 084, отсортирован как знаковые числа; поиск `0x2a6e40`):
  4 458 записей раскладываются как `H("<ENUM>_<Value>")` по строкам eboot (разложение линейное: `H(p+s) =
  H(p)·101^|s| + H(s)`, 101 обратимо по модулю 2⁶⁴), например `cid_MISSION` → 257, `TFN_0`/`TFN_1` → 0/1
  (хеши соседних значений отличаются на 1 — признак полинома без перемешивания);
* 2 709 из 2 710 хешей имён полей рефлексии (`0xd057a0`) совпадают с `H(имя)` напрямую;
* строковые константы скриптов — `H(ключ текста)`: 76 ключей `lang_english_text` найдены в `msn_vor` (§6).

Хеши **имён типов** (`MISSION_DATA` и т. п.) этим хешем не являются (GUID-подобные, как уже отмечено в N11):
значение такой записи словаря — индекс в массиве имён классов. Для рантайма составлена таблица 346 типов,
реально встречающихся в пакетах (`engine/resources/type_registry_table.inc`). Классы в записях линковки
скриптов, наоборот, — значения перечисления `cid_<ИмяКлассаCamelCase>`: `H("cid_GraffitiMinigame")` =
`0x40e9fe2abbcac8e2` [П] — вычисляются без таблицы (`res::ClassIdHash`).

## 2. Классы и рефлексия [A][П]

* Массив имён `0xdac130` (data): четыре параллельные таблицы по номеру класса (`cid`): `NAME`, `NAME_DATA`,
  `CName`, `SNameData`; например 12 `GRAFFITI_MINIGAME`, 125 `GRAFFITI_PROXY_SITE`, 257 `MISSION`,
  289 `OBJECTIVE`, 291 `RULE`, 294 `EVENT_RULE`, 296 `BRIEF`, 315 `STORY`. Индекс типа данных = 512 + cid
  (`MISSION_DATA` = 769, `OBJECTIVE_DATA` = 801).
* Таблица `0xd057a0` (по cid): `{i32 число, указатель на дескрипторы}`, поиск члена `0x4cfcb0` (бинарный по хешу).
  Дескриптор: `+0x00` хеш имени, `+0x08` тип значения (0 void, 1 bool, 2 int, 3 float, 4 point, 5 vector, 7 id/строка,
  8 cid, 0x2002 ссылка …), `+0x0C` флаги (1 метод, 4 геттер, 0x14 свойство, `0xa` поле данных), `+0x10` функция
  метода, `+0x18` **смещение поля в объекте**, `+0x28/+0x38` геттер/сеттер.
* Примеры. `MISSION`: методы `COMPLETE_SUBTASK`, `IS_SUBTASK_COMPLETE`, `COMPLETE_CHECKPOINT`, `FAIL_SCRIPTED`,
  `ABANDON`, `FIRE_TRIGGER_EVENT`, поля `AUTO_START_NEXT_MISSION` (+0x268), `DESCRIPTION_TEXT` (+0x278),
  `RESPAWN_CHECKPOINT` (+0x130), `AWARD_XP` (+0x230), `ALLOW_SYSTEMIC_MISSIONS` (+0x150). `OBJECTIVE`: `Start`,
  `Complete`, `IS_COMPLETE`, `IS_START`, `IS_CHECKPOINT`. `GRAFFITI_MINIGAME`: см. `GRAFFITI_RESEARCH.md`.
* Имена событий жизненного цикла (строки eboot): `MissionStart`, `MissionComplete(Pre/Post)`, `MissionFail(Pre/Post)`,
  `MissionAbandoned`, `MissionRetry`, `ObjectivePush`, `ObjectivePop`, `MiniMissionStart/Complete/Abandoned`.

## 3. Объекты пакета [П]

* Корневой каталог — блок типа 6: `{u32 n, u32 n, n указателей с +8}`, размер блока ровно `8 + 8n`
  (graffiti_a8_family 0x1b0 при n = 53, msn_vor 1 232 объекта). *Уточнение N11: указатели начинаются с +8, не с +0x10.*
* Заголовок объекта: `+0x10` тип (фиксап DIC: в файле 0, хеш в записи DIC), `+0x18` u64 **OID**, `+0x30` указатель
  в каталог, `+0x38` u32 флаги (младшие 16 бит `0xffff` у объектов верхнего уровня), `+0x40` указатель на код
  инициализации (splice). Пространственные объекты: `+0x60` масштаб, `+0x70` кватернион (x, y, z, w),
  `+0x80` позиция в см (x, y, z, 1) **относительно родителя**.
* Рантайм-объект (eboot): локальная позиция `+0x120`, родитель `+0x38`; мировая = матрица сустава родителя ×
  локальная (`pos`-геттер `0x5ac180`, `parent` `0x2e1f20`, `PARENT_ROOT` `0x277700`) [A].
* DIC: `{u32 n, u32 0, n × {u32 место, u32 0, u64 хеш}}` — в место пишется значение из словаря: индекс типа или
  значение перечисления (`0x30a310`/`0x2a6e40`) [A][П]. PYTO: `{u32 место, u8, u8 флаг, u8 вид 0/1/2 → |0x1000/0x2000,
  u8, u64}` — в место пишется значение `cid` (u32 или u16) с флагами (`0x30a910`) [A].
* В мировых чанках позиции объектов — в собственной системе чанка: для `a8` начало = (100, −200, 0) м
  (выведено по камере граффити, проверено тестом `n12_graffiti_placement_matches_original_camera`); в пакетах
  миссий позиции мировые [П].

## 5. Скрипты (splice) и их линковка [A][П]

Логика миссий — скомпилированный код splice (строки eboot: `CSpliceEnv`, `CSpliceThread`, `SPLICE`,
`SPLICE_FROM_FILE`, `CallMissionSplice`). Даже свойства объектов задаются этим кодом (`TRAINER_HINT.text`,
`EVENT_RULE.source`, `CAMERA_ZONE.*`).

Чанк **PLPS** — не «правки свойств», а **таблица линковки** этого кода (`0x30b1c0`): для каждой инструкции
линковщик находит класс по хешу (`0x2a6e40`) и член по хешу имени (`0x4cfcb0`) и переписывает инструкцию на
прямой доступ (смещение `+0x18`, геттер/сеттер `+0x20…+0x48`), вызовы — на санки (`0x30bc00`). Раскладка:

| Таблица | Запись | Поля |
|---|---|---|
| члены (n1, `q[0]` lo32) | 0x18 | `u32 место, u32 0, u64 класс (cid), u64 имя члена` |
| методы (n2, `q[0]` hi32) | 0x30 | `u32 место, u32 смещение аргументов, u64 класс, u64 метод, u64, u64, u8 argc @+0x28` |
| глобальные (n3, `q[1]`) | 0x28 | `u32 место, u32 смещение аргументов, u64 функция, …, u8 argc @+0x20` |

Глобальные функции — таблица eboot `0xda1790` (669 × 0x20: `{хеш, функция, …}`; 33 имени найдено: `ACTIVATE`,
`DEACTIVATE`, `Trigger`, `WaitForSignal`, `Unspawn` …). Инструкция: байт 0 — опкод, байты 2–3 — тип значения.
**Непосредственные операнды** (измерено, `res::Immediate*`): опкод `0x0e` — значение по `loc + 0x18`, выровненное по
типу (4 float, 8 id, 16 point/vector); опкод `0x14` с id — по `loc + 0x28`; аргументы вызова метода — блок с
`align16(loc + 0x30)`. Проверено: константы граффити (§ GRAFFITI_RESEARCH), `TRAINER_HINT.INITIAL_DELAY` = 12,0,
`TRAINER_HINT.text` = `H("u_hint_move")`, `BRIEF.NOTE_TEXT` = `H("u_mininote_vor_escape_cannery")`.

**Не восстановлено [?]:** набор опкодов и семантика виртуальной машины splice (ветвления, ожидания, события,
стек), поэтому порядок шагов миссии из кода не читается.

## 7. Тексты [П]

`lang_english_text.xpps` (вид 7), объект `GAMETEXT`: `+0x40` → 12 091 запись по 0x20 байт `{u64 H(ключ), указатель на
"ключ\0[заголовок]текст", u16…, u8 @+0x15 раскладка}`, сортировка по знаковому хешу; у реплик (`+0x15` = 6) между
ключом и текстом — выравнивание до 2 и четыре u16 (например 1, 6, 125, 8 [?: роли]). Ещё таблицы: `+0x30` (89),
`+0x50` (3 154), `+0x60` (63) [?]. Значки кнопок — символы U+F083 … (`res::GameText`).

## 9. Нерешённые вопросы

1. Виртуальная машина splice (опкоды, ветвления, ожидания, сигналы) — без неё нельзя исполнять миссии игры напрямую.
2. Хеш имён типов (`*_DATA`) — не выведен; используется таблица.
3. Иерархия объектов чанка (кто родитель прокси-сайта/кнопки, таблица OID→объект `0x687e60` в `a8`), правило
   начала координат чанка (100 м тайлы? — для `a8` выведено, общее правило не доказано).
4. Модели `OBJECT_DATA` (`+0x190` → запись модели с шейдерами): здание консервного завода и щит не рисуются.
5. Форма объёмов `VOLUME_BUTTON` (масштаб к какой единичной фигуре применяется).
6. Таблицы `GAMETEXT` `+0x30/+0x50/+0x60`, поля заголовка реплик.
7. Сохранения PS4 — не исследовались (нативный формат, см. N12_CAMPAIGN_RECONSTRUCTION.md).
