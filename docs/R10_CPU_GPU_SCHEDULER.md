## 1. Конвейер: было и стало

Было (preset `play.cmd`), без изменений по умолчанию [E]:

```
Game:Main ──PM4──► GpuNative (CP, поток 1) ──кольцо записей──► GpuFrontend (P53) ──► GpuRecord (T2) ──► GpuEmit ──► драйвер/GPU
     ▲                  │  QueueFull: кольцо к T2 полно              подготовка draw/dispatch    запись Vulkan    vkCmd* в драйвер
     │                  └─ IdleGpu: ждёт GPU                                                         │
  JobWorker1–5                                                                                       ▼
  (job-система игры)                                           VideoOutPresent ◄── flip ◄── GPU (одна очередь, или + AQ lane у pacing)
Фон: 3 потока async graphics (SSPC_ASYNC_PIPELINES) + 2..6 потоков prefetch (SSPC_PIPE_PREFETCH) + прекомпилятор старта
```

Стало (флаги): та же цепочка потоков. Изменились две вещи.

- **Фоновая сборка конвейеров** (`SSPC_R10_SCHED=1`) идёт не на собственных потоках фабрики, а на одном пуле R10:
  N = лог. CPU − 4 воркеров (8 на 12-поточном CPU), приоритет ниже нормального, кража задач. Задачи — «дренажи»,
  не больше одного на воркер для каждого вида работы. Работа не выбрасывается никогда.
- **Тяжёлые потоки** (`SSPC_R10_SPREAD=1`) получают ideal processor, по одному на физическое ядро. Это подсказка
  планировщику Windows, не привязка.

Кадр N/N+1/N+2 [E] (s2, city fight, 45 FPS): CP опережает present не больше чем на 0–1 flip. Батчей в очереди GPU
к моменту present в среднем 1,65 (p95 5). Глубину конвейера ограничивают кольцо записей CP→T2 (`SSPC_CP_RING=128`)
и ожидание GPU потоком CP (IdleGpu). Отдельного планировщика очередей нет: это зона pacing, см. §7.

## 3. Почему GPU простаивает (измерено)

Ниже — что делали потоки CPU во время простоя GPU: 3,81 мс на кадр, 17 % кадра [E]. Данные s2, раздел
«GPU idle … meanwhile» в `timeline_summary.txt`.

- **GpuRecord работает 3,24 мс** из этих 3,81. Внутри простоя GPU 86 мс/с уходит на запись draw (≈3,8 мкс на draw
  в T2) и 43 мс/с на dispatch [E]. Вывод: **запись draw в T2 — критический путь ≈13–17 % кадра в бою** [A].
  Передано cp: их R8-профиль даёт тот же вывод, T2 — «стена» конвейера.
- GpuFrontend работает 2,92 мс; CP ждёт QueueFull 2,14 мс, то есть кольцо к T2 полно [E]. CP и фронтенд не являются
  причиной: они ждут T2.
- Game:Main загружен на 98 % одного CPU, при этом GPU простаивает [E]. Значительная часть этого — спин-ожидания [A].
  Подтверждение: ETW показывает 155 переключений в секунду при 98 % CPU.
- Ожидание compute игрой (REA-3) — отдельная причина, её разбирает pacing (AQ, `SSPC_R10_AQ_*`). Здесь не трогалась.

Предложение pacing (SHARED_NOTES 10:00): раньше отдавать батч в vkQueueSubmit, не дожидаясь конца длинной серии draw.
GPU тогда начнёт раньше, и часть простоя 3,8 мс уйдёт [H]. Это механизм pacing/cp, а не sched.

Холодный кэш (neon, свежие кэши шейдеров и драйвера) [E]: поток записи ждал готовности конвейеров 129,7 с из 133.
Именно это лечит prefetch (§4, §5).

## 4. Переписанные компоненты

1. **`SSPC_PIPE_PREFETCH=1`** (fdfd929, перенос R9-N без изменений логики). Как только фронтенд подготовил dispatch,
   ещё не построенный compute-конвейер ставится в фоновую сборку. T2 при записи забирает готовый конвейер, ждёт
   строящийся или строит сам, если сборка не началась. Dispatch не пропускается.
2. **Пул R10 `SSPC_R10_SCHED=1`** (b427cbc). Устройство: `r10/work_pool.{h,cpp}`. Деки на воркер с приоритетами,
   кража со старого конца, ограничение очереди (backpressure), зависимости `Then`, scratch-арена.
   Фабрика конвейеров использует пул через задачи-дренажи (`Kick`/`SubmitDrainer`). Дренаж берёт самую старую работу
   своего вида, выполняет её и переподаёт себя, пока очередь не пуста. Оба вида работы — Normal.
   - **Первая версия была ошибочной** (инцидент neon_cold_B, §8).
3. **`SSPC_R10_SPREAD=1`** (`r10/spread.{h,cpp}`). `SetThreadIdealProcessorEx` для Game:Main, GpuNative, GpuRecord,
   GpuFrontend, GpuEmit и VideoOutPresent: каждому — первый логический CPU своего физического ядра.
4. **`SSPC_R10_AFFINITY_LOG=1`** (`runtime/kernel/thread.cpp`). В лог пишется приоритет и маска, которые просит каждый
   поток гостя. Маски по-прежнему не применяются.
5. **Таймлайн-профилировщик** (b0ed130, поверх P4.12 `SSPC_P412_STALL_TRACE`):
   - роли Frontend, Emit, Worker;
   - события FrontWait/FrontPrep, EmitWait/EmitRun, PipeBuild, InputEvent, PresentDone, SchedTask;
   - время GPU — калиброванные метки `VK_EXT_calibrated_timestamps`;
   - формат AqSubmit и флаг lane в GpuBatch взяты у pacing один в один.

   Инструменты:
   - `tools/r10/timeline.py` — CSV по кадрам, сводка и Chrome/Perfetto JSON;
   - `tools/r10/cores.py` — ETW CSwitch по ядрам и потокам.

   Накладные расходы: deep без records — около 1 % FPS [H]. Режим records=1 заметно дороже, только для разбора.
6. **Зонд задержки `SSPC_R10_LATENCY=1`**. Момент сценарного ввода берётся в TSC. Presenter копирует сетку 16×9 текселей
   каждого показанного кадра в host-буфер. `tools/r10/latency.py` находит первый present, в котором картинка
   изменилась после поворота камеры.
   - Задержка меряется от SDL-события до возврата vkQueuePresentKHR.
   - Задержка дисплея сюда не входит.

Параллельная подготовка draw (пункт 4 ТЗ) не делалась. Профиль показывает, что фронтенд не на критическом пути:
работает он 2,9 мс внутри простоя GPU, но ждёт T2. Сама запись T2 — Vulkan-команды одного command buffer, её делит cp.

## 6. FPS и 1 % low

**Тёплый кэш** (как играет владелец). Ни один из флагов sched не меняет средний FPS и 1 % low сверх шума
(таблица §5). Предел — последовательная цепочка CP → T2 → GPU (§3), её планировщик фоновой работы не трогает.

**Холодный кэш** (первая встреча эффекта, свежие кэши, neon, окно 42–133 с, n = 1):

| Конфиг | FPS | 1 % low | p99 | max |
|---|---|---|---|---|
| A | 12,9 | 0,32 | 1676 мс | 5,5 с |
| P = `SSPC_PIPE_PREFETCH=1` | 26,1 | 1,26 | 407 мс | 2,5 с |
| B2 = P + `SSPC_R10_SCHED=1` | 25,9 | 1,40 | 388 мс | 1,55 с |

Здесь prefetch — единственное реальное улучшение ветки: FPS ×2, p99 в 4 раза меньше. Пул поверх prefetch дополнительно
снижает max фриза (2,5 → 1,55 с) и чуть поднимает 1 % low. При n = 1 это **не доказано**.

Цена prefetch на холодном кэше: «draws skipped while building» на кадр выше, чем у A (42 против 28). Пока
графический конвейер строится, кадров успевает пройти больше. У B2 таких пропусков 31,2 тыс. на 2357 кадров, то есть
13 на кадр — меньше, чем у A.

## 10. Рекомендации для play.cmd

- **play.cmd не менять.** На тёплом кэше ни один флаг sched не даёт выигрыша (§5). Приоритет — плавность, а значит
  включать по умолчанию нечего.
- `SSPC_R10_SPREAD` — **не включать**: выигрыша нет, traverse 1 % low хуже на 2 FPS (n = 2).
- `SSPC_PIPE_PREFETCH=1` — кандидат для первого прохождения и после обновления драйвера, когда кэш холодный:
  ×2 FPS и p99 в 4 раза меньше на холодном neon. Рекомендую включить его отдельной серией pacing/координатора на
  холодном кэше с n ≥ 3 в нескольких сценах. Пока n = 1 — **NOT TESTED** как рекомендация.
- **play_experimental.cmd**: можно добавить `SSPC_PIPE_PREFETCH=1` (на тёплом кэше ничего не делает, на холодном
  ×2 FPS), с пометкой «первое прохождение / новый драйвер». `SSPC_R10_SCHED` и `SSPC_R10_SPREAD` туда не добавлять.
- `SSPC_R10_SCHED=1` — только вместе с prefetch и только после той же холодной серии. После фикса дренажами мир
  на холодном и тёплом кэше рисуется (§5, §8). Валидация Vulkan с ним — см. §8.
