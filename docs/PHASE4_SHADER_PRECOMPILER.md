# P4.14 — постоянный кэш шейдеров и прекомпилятор при запуске

Дата 2026-10-12. База — `6e13a05` (интеграция ПК-настроек). Коммиты этапа: `b179ae3` (кэш, manifest, VkPipelineCache,
прекомпилятор, трасса, меню F1) и следующий за ним (порядок по использованию, индекс программ игры, диагностические
переключатели, тестовые скрипты, отчёты). `--gpu-backend sspc`, Ryzen 5 5500 + RTX 2060 6 ГБ, 32 ГБ без файла подкачки,
Windows 10, драйвер NVIDIA. Файлы игры (`E:\shdps4\CUSA00004`), `play.cmd`, `tools\manual_run.ps1`, worktree
`E:\SecondSonPC-task2` не менялись, push не делался. Логи — `logs\p414\m1\` (матрица, `report.md`), `logs\p414\cases*\`
(отказы и совместимость). Офлайн-анализ файлов игры — `docs\OFFLINE_SHADER_PRECOMPILATION.md`.

**Итог.**
- **Причина многосекундных зависаний доказана трассой:** это создание графических конвейеров драйвером при первой
  встрече. Трансляция GCN→SPIR-V тут ни при чём.
  - Холодный запуск (A, деревня): 583 конвейера созданы на ходу, суммарно 41,6 с; один конвейер — до 318 мс; кадры до 24,5 с.
  - Из кадров ≥100 мс на деревне, пляже и гавани у 52 из 53, 40 из 42 и 35 из 36 поток записи больше половины кадра
    занят компиляцией. Трансляция занимает 0,9–1,4 с за прогон.
- **Повторный запуск с P4.14 (CW) против повторного запуска до P4.14 (R)** — 90 с, деревня / пляж / гавань:
  - кадров ≥100 мс: 7 / 5 / 10 → 4 / 4 / 3;
  - 1% low: 5,5 / 7,2 / 4,8 → 7,7 / 10,3 / 7,9 FPS;
  - самый длинный кадр: 2,7 / 2,3 / 2,8 → 1,8 / 1,7 / 1,8 с;
  - кадров ≥100 мс с компиляцией больше половины кадра: 2 / 1 / 4 → 0 / 0 / 0.
- **Собственный кэш драйвера очищен, `vulkan.bin` цел (C):** прекомпиляция при старте занимает 1,0 / 0,9 / 1,1 с. В
  игре на ходу 0 / 0 / 6 конвейеров. Без прекомпиляции (B) на ходу уходит 1,6–2,4 с, на холодном старте (A) — 25–42 с.
- **Обновление драйвера (D):** `vulkan.bin` отбрасывается, 585 конвейеров деревни собираются из SPIR-V кэша за 9,9 с

- **Оставшийся кадр ≥1 с** — первый кадр уровня (1,8 с записи загрузки), а не шейдеры: в CW кадров с компиляцией 0.
- **Первое посещение новой локации** кэш P4.14 ускоряет только частично. Конвейеры, которые он ещё не видел, создаются
  на ходу, как раньше. По трём сценам 67 / 87 / 69 % конвейеров сцены уже есть в кэше двух других (общие эффекты,
  интерфейс, персонаж). Предсказание остального по файлам игры измерено и не включено — см. офлайн-отчёт.

## 1. Аудит (что было до P4.14)

- **Фронтенд шейдеров (`shader_frontend`, `shader_cache`).**
  - Кэш программ по содержимому: XXH3-128 кода + длина + аппаратная стадия.
  - Модули (SPIR-V) кэшируются по `SpecializationKey`; трансляция идёт на рабочих потоках.
  - Всё в памяти, при перезапуске теряется.
- **`PipelineFactory`.**
  - Конвейеры создаются синхронно на потоке записи команд с `VK_NULL_HANDLE` вместо pipeline cache.
  - Единственный кэш между запусками — собственный кэш драйвера NVIDIA (`%LOCALAPPDATA%\NVIDIA\GLCache`). Он
    сбрасывается при обновлении драйвера, и на нашей стороне его не проверить.
- **Как воспроизвести холодный драйвер.** `__GL_SHADER_DISK_CACHE_PATH` на пустую папку переназначает GLCache только
  для процесса. Так получены конфигурации A, B, C и сценарий D без вмешательства в систему.

## 2. Диагностика `SSPC_SHADER_STALL_TRACE=1[,event=мс][,frame=мс][,wait=мс]`

`src\runtime\gpu\shader_trace.{h,cpp}`.

**Что пишется.** События по видам:
- трансляция;
- чтение и запись диска;
- создание `VkShaderModule`;
- создание конвейера, отдельно на ходу и готового от прекомпилятора;
- прекомпиляция;
- загрузка и сохранение кэша;
- ожидания.

У каждого события: начало и конец (TSC, общий отсчёт с `gpu_frames.csv`), поток, кадр, ключи шейдера и конвейера,
флаги (compute, попадание в кэш драйвера по `VkPipelineCreationFeedback`, ожидание прекомпилятора, ошибка).

**Как пишется.** Горячий путь только кладёт запись в буфер под коротким mutex. Файлы сбрасывает отдельный поток раз в
250 мс.

**Пороги.** Событие — ≥10 мс; кадры — ≥100 мс и ≥1000 мс считаются отдельно. Ожидания из P4.12 (`stall_trace`) длиннее
порога пробрасываются в ту же трассу (кроме записи, vblank и самих компиляций), поэтому видно, чего кадр ждал.

**Файлы** (`logs\`):
- `shader_stall_events.csv`;
- `shader_stall_frames.csv` — по каждому долгому кадру: сколько из него занято компиляцией и трансляцией;
- `shader_stall_frames.txt` — разбор худших кадров;
- `shader_stall_summary.txt`.

## 3. Дисковый кэш SPIR-V — `shaders.pack`

`src\runtime\gpu\shader\shader_disk_cache.{h,cpp}`.

**Путь.** `cache\shaders\CUSA00004\native\<поколение>\shaders.pack`, рядом `vulkan.bin`.

**Поколение.** 16 hex — хеш от:
- исходников транслятора и фронтенда (считается при configure CMake, `SSPC_NATIVE_SHADER_GENERATION`);
- поколения моста shadPS4;
- профиля устройства (то, что влияет на SPIR-V);
- версии формата.

Изменился транслятор → новый каталог, старый SPIR-V не используется. Хранятся три последних поколения (A/B разных
сборок), более старые удаляются при запуске. Каталог, который сейчас используется, не трогается никогда.

**Формат.** Добавляемый в конец (append-only) журнал:
- заголовок 64 Б (`SSPCSHC1`, версия, поколение);
- записи `{'SPRC', тип, размер, XXH3 содержимого}`.

**Типы записей:**
- `P` — программа: идентичность по содержимому, футер, GCN-код;
- `S` — SPIR-V: хеш128 и слова, хранится один раз (дедупликация);
- `M` — модуль, полный ключ:
  - идентичность программы;
  - номер раскладки;
  - `RuntimeParams` целиком (с размером структуры);
  - start;
  - user_data 64 Б;
  - слова и хеш `SpecializationKey`;
  - хеш SPIR-V;
  - reflection, flatbuf, fetch-код, vertex sharps;
  - время трансляции;
- `L` — конвейер (`PipelineDesc`, см. §5) и время его создания;
- `U` — использование: сколько запусков подряд конвейер был нужен.

**Целостность и восстановление.**
- **При открытии** каждая запись проверяется по XXH3. С первой битой или оборванной файл обрезается: хвост с этого
  места отбрасывается, всё до него используется.
- **Повреждённый заголовок или чужое поколение** — файл начинается заново.
- **Два процесса.** Lock-файл с `FILE_FLAG_DELETE_ON_CLOSE`: второй процесс получает кэш только для чтения.
- **Запись** идёт в фоне одним потоком, на горячем пути ничего не ждёт.

**Модуль из кэша используется только при совпадении всего ключа.** При первом обращении программы создаются заглушки
модулей. Модуль загружается при постановке в очередь трансляции — только если совпадают `RuntimeParams`, start,
раскладка и все слова ключа. Иначе модуль транслируется заново, как раньше.

**Лимит размера.** `maxSizeMiB`, по умолчанию 2048. Сверх лимита новые записи не пишутся (`dropped_full` в статистике),
игра работает как без кэша. По факту кэш на сцену — 17–25 МиБ.

## 4. `VkPipelineCache` — `vulkan.bin`

`src\runtime\gpu\vulkan\vk_precompile.{h,cpp}`, `PipelineCacheFile`.

**Заголовок 64 Б** (`SSPCVKPC`): vendor, device, версия драйвера, `pipelineCacheUUID`, размер, XXH3 данных.

**Чужое устройство или драйвер, повреждение, отказ драйвера** — создаётся пустой кэш, в лог пишется причина
(«written by another driver» и т. п.).

**Сохранение** атомарное: `.tmp` + `MoveFileEx(REPLACE_EXISTING|WRITE_THROUGH)`.
- Когда: при остановке и в игре. Раз в 10 с проверяется, были ли новые конвейеры. Если были и 10 с новых не
  появлялось — кэш сохраняется, но не чаще раза в минуту.
- Если сохранение прервано, старый `vulkan.bin` цел. Проверено сценарием F3/F4.

Один кэш на все потоки: и прекомпилятор, и создание на ходу передают его в `vkCreate*Pipelines`.

## 5. Manifest конвейеров

Запись `L` = `PipelineDesc`. Хендлов и указателей в ней нет:
- хеши SPIR-V стадий;
- `GraphicsPipelineState` без внутренних id;
- fs_runtime;
- привязки `(binding<<32)|(type<<16)|count`.

Конвейер описывается тем же кодом, которым его создаёт исполнитель (`PipelineFactory::DescribeGraphics/Compute` →
`Build`). При повторной встрече того же описания в одном запуске — `desc_reuse`. Записи `U` дают порядок прекомпиляции:
сначала конвейеры, нужные в большинстве запусков.

## 6. Прекомпиляция при запуске

`PipelinePrecompiler`.

**Что собирается.** Каждый конвейер из manifest, у которого все стадии есть в кэше SPIR-V. Ничего не угадывается. У
каждой записи своё состояние с CAS-переходами: ожидает / строится / готов / ошибка / забран потоком записи.

**Потоки.**
- До старта игры: по умолчанию половина логических процессоров, не больше 6 (на Ryzen 5 5500 — 6). Число задаётся в
  `precompileThreads`.
- Когда игра запущена: 2 потока с `BELOW_NORMAL`, доделывают оставшееся.

**Ожидание при старте.**
- До конца сборки, но не дольше `precompile_max_s` (300 с).
- Esc — пропустить: остаток собирается в фоне, в логе «skipped by the user».
- Если конвейеров меньше 0,25 с работы, панели нет.

**Панель.** Оверлей меню поверх окна. Строки: «Подготовка шейдеров», «Подготовлено N / M (p %)», «Компиляция
графических конвейеров…», затраченное время, ошибки. Все числа — из реального состояния записей. В автоматических
прогонах (`--press`) панели нет, а расписание нажатий сдвигается на время паузы.

**Конвейер нужен игре раньше, чем его собрал прекомпилятор:**
- уже готов — берётся;
- строится сейчас — поток записи ждёт его (собирать заново дольше), ожидание считается;
- ещё не начат — поток записи забирает запись себе и создаёт конвейер как раньше.

Конвейер никогда не собирается дважды. Готовый конвейер выдаётся только при побайтовом совпадении описания.

## 7. Новые шейдеры

Путь не изменился: трансляция → модуль → конвейер на ходу. Кэш и manifest только дописываются. Draw не пропускается и
не подменяется. Если модуля нет, ведётся то же ожидание трансляции, что и до P4.14.

## 8. Меню F1 → «Шейдеры и кэш»

Категория в существующем меню ПК-настроек (`registry.cpp`, `Category::Shaders`). Настройки (`SecondSonPC.toml`, `[pc]`):

| настройка | по умолчанию |
|---|---|
| `shader_precompile` | вкл. |
| `shader_precompile_progress` | вкл. |
| `shader_cache_max_mib` | 2048 |
| `shader_precompile_threads` | 0 (авто) |

Строки статистики:
- размер кэша;
- «шейдеров: N, конвейеров: M»;
- последний запуск: собрано, ошибки, время;
- «программ игры: X из Y» — из индекса `--scan-game-shaders`.

Команды «Очистить кэш шейдеров» и «Очистить кэш конвейеров Vulkan»:
- требуют второго нажатия для подтверждения;
- пишут `clear_*.request`, а очистка выполняется при следующем запуске, до открытия кэша: открытые файлы не удаляются.

**Переключатели:**
- `SSPC_SHADER_PRECOMPILE=0|1`;
- `--no-shader-cache`;
- `--shader-cache <каталог>`;
- `--clear-shader-cache`.

**Диагностика** (только тесты):
- `SSPC_DIAG_PIPELINE_CACHE_DRIVER=<hex>` — подменить версию драйвера, «чужой» `vulkan.bin`;
- `SSPC_DIAG_PIPELINE_CACHE_TEAR=<байт>` — прервать сохранение `vulkan.bin` и завершить процесс;
- `SSPC_DIAG_SHADER_CACHE_TEAR=<байт>` — оборвать запись `shaders.pack` и завершить процесс.

## 9. Что не сломано

- **Самотест:** группа `Shader(disk)` — 11 проверок (обрезка хвоста, чужое поколение, только чтение, совпадение
  ключа, атомарность `vulkan.bin` и др.).
- **Меню F1:** снимок `ru_1080_shaders.png` в тестах настроек.
- **Прочее** (B, Parallel CP, валидация) — сценарии G и V в §10.

Stage memo, GPU timestamps, трасса P4.12 и SSPC-020/wave64 не затронуты по коду: фронтенд меняется только на входе
`Enqueue` (загрузка) и после трансляции (запись). Новые оптимизации GPU не включались. Кэш и прекомпиляция включены по
умолчанию, потому что создают те же конвейеры тем же кодом; отключаются одним переключателем.

## 11. Ограничения

- **Первый визит не покрыт.** Помогает только то, что уже встречалось в одном из прошлых запусков (на этой машине,
  или кэш перенесён с машины с тем же GPU-профилем).
- **Обновление драйвера** стоит одной полной прекомпиляции при следующем запуске: 9,9 с на 585 конвейеров (D), растёт
  с размером кэша. Esc переносит её в фон; тогда ещё не готовые конвейеры создаются на ходу.
- **Новая сборка с изменённым транслятором** — новое поколение, кэш набирается заново.
- **Первый кадр уровня** (~1,8 с записи) остаётся. Это не шейдеры, а объём первого кадра — отдельная задача.
- **Покрытие не 100 %.** На гавани в C 6 конвейеров появились впервые и были созданы на ходу.

## 12. Дальше

- Кэш, собранный за полное прохождение, — это готовый manifest для всех. Он переносим между машинами с тем же
  профилем устройства. Чужой драйвер он не ломает: `vulkan.bin` отбрасывается, SPIR-V и manifest остаются.
- Предсказание конвейеров до первого визита по файлам игры — `docs\OFFLINE_SHADER_PRECOMPILATION.md`.
