## 1. Итог

1. **Пакеты commit дешёвые; дорого то, что CP выводит из них заново.** На draw в городе CP разбирает 4,23 `SET_SH_REG`
   и 3,91 `NOP` (≈ 51 тыс. и ≈ 47 тыс. за кадр при ≈ 12 тыс. draw); по замерам R6-P это 1,8–2,8 мс и ≈ 1,3 мс потока 1
   (с накладными расходами замера), из них маркеры `NOP 0x6875000D` (нулевая информация для CP) — 0,4–0,9 мс [E + H].
   Удешевление цикла пакетов уже мерилось (`SSPC_CITY_ENGINE_AHEAD`) и прироста не дало. Пропускать разбор
   `SET_SH_REG` commit нельзя по правилу 1 §5.2 CORE (регистры — источник истины, поток 2 живёт журналом регистров).
2. **Двойная обработка — во фронтенде потока 1:** commit кладёт тень в **новый** снимок → новый указатель в user data →
   промах памятки стадий P4.7 («other user data» 12,8–13,7 млн за прогон) → обход SRT по гостевой памяти (45 чтений на
   подготовку draw, 721 млн за прогон) → декодирование → ключ → модуль (попаданий 33,6 млн, промахов 0). У 26 % / 33 %
   полных обходов VS/PS результат равен прошлому (R6-P), версия привязки сохраняется у 41,7 % снимков PS и 0,13 % VS
   (R7-R). Оценка сверху пользы версии как ключа — ≈ 1,8 тыс. подготовок PS на кадр, ≤ 1,6 мс потока 1 [H]; мерить A1.
3. **Прочие писатели user data не меняют правило версии.** Все графические писатели user data в eboot — три Gnm-помощника
   (`0x626400`, `0x626490`, `0x626520`) и пять их встроенных вариантов без ссылок. Обработчики `0xb8d0…0xba20`
   (таблица указателей на методы `0xcc8000`) и `0xbe40` принадлежат **отдельному объекту** (свой DCB в `[объект+0]`, не
   `CUE+0xC090`) и лежат в статически изолированном участке `0x5af0…0x11560` + `0x19050`: ни одного вызова, ни одного
   RIP-относительного адреса, ни одной релокации на его входы извне; экспортов у eboot нет. Достижимы по DCB контекста R
   только commit `0x14ad0`, 7 сеттеров (бит 15) и CS-commit `0x13ec0` (регистры COMPUTE_USER_DATA, не VS/PS).
   Правило «версия действительна только при наблюдаемом commit» остаётся, но **достаточно** ключа «версия + user data
   по значению + проверка, что указатели формы равны `snapshot + смещение·4`, которые видит CP» (§6).

## 2. Аудит жизненного цикла CUE (перенос из `E:\research\r8\recomp\STATUS.md`, статический разбор eboot) [A]

Поиск ссылок: прямые call/jmp/jcc rel32/rel8, RIP-relative операнды, релокации с addend = адрес, сырые u32/u64 по образу
(`tools\xrefs.py`, `funcs.py` — границы функций по `.eh_frame_hdr`, `fields.py`, `around.py`, `disx.py`).

1. **Init `0x13a50`**: `R::Init 0x11efc0` → `0x18090` → `0x13a50`; только при запуске (`0x29c420` → `0x1ef980`: пре/пост и
   254 слота пула, флаг «инициализировано» в `0x196746`; `0x16f460`: 5 контекстов деформации). memset тени **не меняет
   cv** — если Init пройдёт по уже отслеживаемому CUE, binding-версия может сохраниться при других байтах.
   Предложение: входная проба на `0x12210` (вызывается `0x13a50` до memset; пролог 15 байт без переходов и RIP-relative,
   FNV `0xa09a019a7ee21958`) → `Forget`.
2. **Reset `0x13da0`**: хвостовой jmp из `0x18170`, каждый кадр из `0x1f14e0` внутри `SubmitFrame 0x1f1e30`; = `0x12390`
   (поворот кольца ≤ 4 кусков аллокатора) + тело `0x13d20`. Проба R7-R на `0x12390` срабатывает до обнуления полей
   (сейчас безвредно: `OnReset` поля не читает). **Важно:** после сброса binding-версия может сохраниться (равные байты),
   а адрес снимка новый и старая память снимков переиспользуется после поворота кольца ⇒ **потребитель не может строить
   ключ на адресе снимка и хранить в плане адреса гостя**; правило 4 §5.2 CORE («инвалидация при сбросе») текущей
   версией не выполняется — нужна эпоха сброса (A2) или учёт сброса у потребителя.
3. **ResetShaders `0x13d20`**: из `R::Reset 0x11f050` (каждый кадр из `0x1f14e0` в цикле по пулу, из `0x170980`
   деформация, из `0x1f0be0`); `0x11f050` перед этим обнуляет CUE+0x20..+0x37 (аллокатор) и CUE+0xc1e0 — проба на входе их
   покрывает.
4. **`0x16fb0`**: SGPR сразу в DCB через `0x626520`, мимо тени, без грязного флага, вне наблюдаемого commit; единственный
   вызывающий `0x192890` (ссылок на него не найдено — достижимость не доказана). Версия эти записи не покрывает;
   `direct[]` может держать устаревшие значения прошлой раскладки (`direct_mask` при смене шейдера не очищается).
   Пролог 14 байт пробиваем. **Потребитель обязан сравнивать user data по значению** (исключить можно только SGPR
   указателей формы).
5. **`0x16970`** — один вызов из `0x454230` (PS). **`0x169a0` — вызовы не найдены** (прямые, RIP-relative, релокации, сырые
   u32/u64, символы; «Entry Point EXTERNAL» в Ghidra — не вызов); недостижимость не доказана. Обе безусловно ставят
   грязный байт; commit видит изменение через сравнение user data.
6. **Смена шейдера**: `0x165b0`/`0x16690` — только из `R::SetShaderPair 0x11f3c0` (← `0x447fa0`, `0x448260`); CS — `0x16780`
   из `0x11f520`. Сеттеры ES/GS/HS/LS `0x15c60, 0x15cb0, 0x15d00, 0x15f40` (меняют и раскладку VS), `0x161d0, 0x16200,
   0x16230, 0x162f0, 0x16340, 0x16470, 0x16680` (пишет +0xc130/+0xc168 без грязного флага), `0x167c0, 0x16910`; сброс стадии
   `0x13e30` (обёртки `0x19100`… без ссылок) — вызовы не найдены.
7. **Второй commit `0x140d0`** (полный снимок VS/PS с указателями, гасит грязные байты): только из `0x18210`, ссылок на него
   не найдено. Если выполняется: `Fill` ловит смену содержимого (`fills_stale`), но **не** смену только user data
   (одиночные значения, +0xc130, +0x78) — отдаст старую привязку со старой версией. Подстраховка: в `Fill` сравнивать
   CUE+0x20 (указатель аллокатора) с запомненным в конце наблюдаемого commit.
8. **Прочие писатели user data** — разобраны в §4 (раньше было [?]).
9. DATA-ссылки Ghidra на `0x13d20`/`0x13da0` из `0x596xxx`/`0x597aed` — смещения полей структуры, не вызовы.

Выводы для механизма CP: ключ переиспользования **не** может опираться на адрес снимка или на версию без эпохи сброса;
user data сравнивать по значению (CP и так их видит в регистрах). Версия Native Resource State — подсказка «содержимое
тени не менялось» только в пределах одной эпохи (между сбросами `0x12390`/`0x13d20`) и только при наблюдаемом commit;
Init/второй commit/неизвестные писатели → потребитель должен уметь проверить (verify) и откатиться.

## 3. Gnm-писатели commit `0x14ad0` (п.1 задания) [A]

### 3.1 Командный буфер (G, `CUE+0xC090`) и таблица стадий

Объект `Gnm::CommandBuffer`, который получают `0x626400/0x626490/0x626520`: `+0x08` конец, `+0x10` текущая позиция
(свободно `(end − cur)/4` dword), `+0x18` колбэк нехватки `bool (*)(cb, dwords, user)`, `+0x20` его данные. При нехватке
вызывается колбэк; **если он вернул false — пакет молча не пишется** (ни ошибки, ни маркера).

Регистр стадии: `offset = sgpr + base[stage] − 0x2C00`, `base` — таблица u16 `0xaf0070`:
CS `0x2E40` (COMPUTE_USER_DATA_0), PS `0x2C0C`, VS `0x2C4C`, GS `0x2C8C`, ES `0x2CCC`, HS `0x2D0C`, LS `0x2D4C`.
Бит 1 заголовка (shader type = compute) ставится только для стадии 0 (`sete cl; lea ecx,[rcx+rcx+…]`).

| прямые V#/T# сеттеров (бит 15, `0x626520`) | да: наблюдатель сеттеров («direct» 55,2 млн) | нет (то же) |
| маркер `NOP 0x6875000D` | — (не несёт информации) | **да** — но его пишет игра; см. ниже |
| программа VS/PS (PGM_LO/HI, RSRC1/2) и `SPI_PS_INPUT_CNTL` | да: объекты шейдеров `CUE+0xC0A8/+0xC0B0`, `+0xC168`, `0x638540` | нет; можно не искать программу/модуль заново (`programs: lookups 16,5 млн`, модули — 0 промахов) |

Вывод по п.1: **пакетов, которые CP мог бы не декодировать без потери правильности, — только маркеры
`0x6875000D` (1,2–2,9 на draw).** Их убирает либо нативный commit (`recomp_14ad0` пишет `SET_SH_REG` без маркера —
NOP без эффекта для GPU, CP его игнорирует; нужно доказательство «DCB без маркера ≡ DCB с маркером» в режиме verify),
либо быстрая ветка в `Execute(Nop)` (`p.size()==2 && p[1]==0x6875000D` до `IsMarker`/`ClassifyNop`). Потолок —
0,4–0,9 мс/кадр по ценам R6-P с накладными расходами замера; опыт `SSPC_CITY_ENGINE_AHEAD` (тот же класс пакетов
исполнялся без общего `Step`: B ≈ A, D против C в шуме) говорит, что реальный выигрыш ниже порога измерения.
Замена всех пакетов commit одним маркером «Registers» уже есть (P5.3C, `NativeMarker` → `RegWrite`) и в составе
P5.3 hybrid отвергнута (−4,4 FPS) — без новой гипотезы не повторять.

### 4.2 Виртуальные обработчики `0xb8d0, 0xb970, 0xb9a0, 0xb9f0, 0xba20` и `0xbe40`

- Таблица `0xcc8000` — массив указателей на методы C++ по 16 байт `{функция, смещение this = 0}`, индекс — u16 тип записи
  ресурса. Заполнены (все с релокацией `R_X86_64_RELATIVE`): 0x14 `0xb8d0`, 0x1a `0xb900`, 0x1b `0xb940`, 0x30 `0xba20`,
  0x31 `0xba70`, 0x34 `0xb9a0`, 0x35 `0xb9d0`, 0x36 `0xb970`, 0x48 `0xb9f0`. Базу таблицы берёт только `0xbe40`
  (`lea rbx,[rip+…]` в `0xc7f3`, цикл по записям шагом 0x30 → `call rcx` с `(this, байт, &контекст)`).
- Обработчик: `rdi` = объект, `esi` = индекс, `rdx` = контекст {таблица, стадия `+8`, данные `+0x10`/`+0x18`}. DCB —
  **`[объект+0]`**: `0xb8d0` → `0x626520([obj], stage, sgpr, data+0x3dc, n)`; `0xb970` → `0x626400(…, [ctx+0x18])`;
  `0xb9a0`/`0xb9f0`/`0xba20` → `0x626400` указателей из полей объекта `+0xe488` / `+0xe580` / `+0xe3f0` (последний после
  `0x9050(obj+0xe3e8, 1)`); `0xb9d0` пишет указатель в память контекста (не в DCB). `0xbe40` и `0x9e20`/`0xa350`/`0xab80`
  тоже пишут через `[объект+0]`; блоки стадий по 0x450 байт, маски грязи `+0xe56a/+0xe56b`, предвыборка `0x623630` —
  раскладка «лёгкого» CUE (по виду LCUE Gnmx), **не** CUE контекста R (у того DCB в `+0xC090`, тень `+0x90 + st·0x1800`).
- Вызывающие `0xbe40`: `0x5b40` (← `0x5af0` ← `0x11000`), `0xcd40` (← `0x19050`), `0xd100` (ссылок нет). `0x19050`
  (`0xcd40(rbx+0x120)`, затем Gnm `0x625290(rbx,…)` — rbx здесь сам командный буфер) — ссылок нет. `0x11000` — только
  невыровненные сырые совпадения в данных (`0xd5c457…`), не указатели.
- Проверка изолированности (`tools\island.py 5af0 11560`, `q\island_5af0.txt`; `island.py 19000 19400`): извне на начала
  функций участка — только 9 указателей таблицы `0xcc8000` (её читает лишь `0xbe40` внутри участка) и вызовы из `0x19050`;
  выровненные «указатели» `0x8000`/`0x10000` без релокаций — константы размеров. У eboot нет экспортов и определённых
  символов (`parse_module`: exports 0, symbols с адресом 0), так что извне по имени войти нельзя. Указатель на функцию в
  данных PIE-образа требует релокации, адрес в коде — RIP-относительного операнда; ни того, ни другого нет.

**Ответ:** DCB этих обработчиков — DCB отдельного объекта, не `CUE+0xC090`; участок статически недостижим (вызовы
не найдены ни одним из четырёх способов; недостижимость в строгом смысле — динамически вычисленный адрес — не
доказана, как и для `0x169a0`). Если бы он исполнялся на том же командном буфере, его записи были бы такими же
«неизвестными писателями user data», как `0x16fb0`: CP увидит их в регистрах.

### 4.3 Влияние на правило «версия действительна только при наблюдаемом commit»

Правило остаётся, новых писателей тени/снимка не найдено (R7-R verify: 16,5 млн проверок тени и 9,0 млн same-version —
0 нарушений). Все найденные «прочие» писатели меняют только **регистры** user data, а не байты снимка; поэтому ключ
потребителя, где user data входят **по значению** (правило 3 §5.2 CORE), от них защищён. Небезопасен только ключ «версия
без user data» или «версия + адрес снимка». Добавляется одна деталь: CS-commit `0x13ec0` и `0x132b0` берут память из того
же аллокатора `0x123d0` (у `0x132b0` — свой объект), т.е. адреса снимков VS/PS между commit сдвигаются и диспатчами;
это ещё одна причина не опираться на адрес.

## 5. Дублирующая обработка состояния (п.3 задания) [E + A]

Цепочка для одной стадии: сеттеры пишут тень (38,9 % вызовов — те же байты, R7-R) и **безусловно** ставят грязный байт →
commit копирует тень в новый снимок и пишет новые указатели → CP: `SET_SH_REG` → `RegisterFile` (запись меняет значение
лишь в 34 % случаев) → `BuildDraw` копирует user data → серии Phase 5/6 или полная подготовка → P4.7 по 16 dword
промахивается на новом указателе → обход SRT читает снимок → декодирование дескрипторов → ключ специализации → модуль /
конвейер (найден всегда).

полных подготовок — до 0,417 × 4,3 тыс. ≈ 1,8 тыс. на кадр; ресурсная часть подготовки (обход SRT 13 % + декодирование

`SSPC_CITY_ENGINE_AHEAD` (в шуме).

## 6. Выводы для A2 (Native CP) и A3 (Native Render Layer)

**A2 (Native CP).**
1. Не строить механизм «не декодировать `SET_SH_REG` commit»: правило 1 §5.2, журнал потока 2, и потолок ≈ 2–3 мс/кадр
   уже проверенного класса (AHEAD — в шуме). Маркеры `0x6875000D` — единственный пакет без потребителя; быстрая ветка в
   `Execute(Nop)` безопасна, но ниже порога измерения — по желанию, отдельно.
2. Рычаг — вокруг `PrepareDraw`/`PrepareStage` (снаружи `shader/*`): ключ плана стадии = программа (адрес + RSRC1/2) +
   binding-версия стадии (≠ 0) + 16 dword user data **по значению**, где SGPR указателей формы заменены проверкой
   `user_data[sgpr..sgpr+1] == snapshot + u16·4` из той же записи движка (это и привязывает запись к draw, и закрывает
   переиспользование адресов после поворота кольца, и второй commit `0x140d0`, и `0x16fb0`) + поколение памяти фронтенда
   для памяти, которую обход читает **вне** снимка (глобальная таблица `CUE+0x78`, константные буферы). Многовходовая
   таблица по этому ключу, verify — полный путь + сравнение плана. Потенциал по оценке ≈ 1,8 тыс. подготовок PS/кадр,
   ≤ 1,6 мс сверху — сначала измерить секциями A1 (`PrepareStage` resources).
3. Эпоха: в запись движка — номер сброса (`0x12390`/`0x13d20`, пробы R7-R) и эпоха кадра; при несовпадении — полный путь.
4. CS: `0x13ec0` — тот же механизм; памятка CS промахивается 1,05 млн раз «other user data» — кандидат после VS/PS
   (нужна версия стадии 0 в Native Resource State).
5. `inline_sharps_` не отражает прямые V#/T# сеттеров (маркер `0x6875000D`, не `0x68750004..6`) — на него не опираться.
6. Для точных цифр п.3.4 — счётчик `NOP 0x6875000D` и `SET_SH_REG` по диапазонам USER_DATA (можно в режиме профайлера).

**A3 (Native Render Layer).**
1. В `NativeDrawCommand` на стадию VS/PS: `version` (0 = нельзя), `snapshot`, форма (SGPR → смещение в снимке), значения
   прямых SGPR и маска, программа (адрес + RSRC1/2), эпоха сброса/кадра — по значению, без указателей на объекты движка.
   CP проверяет запись против регистров (п. A2.2), поэтому неточность записи даёт только полный путь, не ошибку.
2. Связь записи с draw — через существующую метку Phase 5 в хвостовом NOP драйвера (индекс в таблицу кадра, которая
   заполняется до `SubmitFrame`, правило 2 §5.2) — без новых слов PM4.
3. Диспетчеризация `0x14ad0` — один механизм; участок LCUE (§4.2), второй commit `0x140d0`, `0x16fb0` статически не
   достижимы — отдельной обработки не требуют, но `Fill` обязан давать `version = 0` при `fills_stale` и не опираться
   на адрес снимка между commit (сдвигают и CS-commit, и `0x132b0`).
4. Если A3 решит убирать маркеры `0x6875000D` в нативном commit — только как отдельный флаг с verify «тот же набор
   регистров» и замером; ожидаемый эффект ниже шума (§3.5).
